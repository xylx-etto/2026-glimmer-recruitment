> 记录实现「对象序列化与反序列化」这道题时，从写第一行到跑通的全过程：想过什么、错在哪、最后怎么改对的。

> 环境：JDK 27 / Windows 11

## 一、题目要求

把 `Student` 对象**写入文件**，再从文件里**读回来**，验证数据完整——即练习 Java 原生序列化。

- 用 `ObjectOutputStream` 把对象写进 `student.dat`
- 用 `ObjectInputStream` 把它读回来，打印验证

---

## 二、整体思路的演变

| 阶段 | 我当时的想法 | 后来发现的问题 |
| --- | --- | --- |
| 1 | 直接用 `new ObjectOutputStream(new FileOutputStream("student.dat"))` 包一层，先把 try 块搭起来 | `Student` 没实现 `Serializable`，`writeObject` 一调就炸；空 try 体还留下一个只有 4 字节的文件 |
| 2 | 补上 `implements Serializable`，直接跑 | 文件不知道跑哪儿去了——相对路径跟着**工作目录**走，不跟源码走 |
| 3 | 读的时候写 `new FileInputStream("Student.dat")` | 大小写不一致。Windows 不区分大小写，侥幸跑通；换 Linux/macOS 必炸 |
| 4 | 不写 `serialVersionUID`，用编译器自动生成的 | 改一个字段，号就变，之前存的文件直接读不了（`InvalidClassException`） |
| 5 | 写死 `serialVersionUID = 1L`，再加字段验证 | 旧文件仍然读得回来，新增字段读出 `null` ✅ |
| 6 | 调试时把写入那段注释掉，只跑读 | 改了类结构却忘了放开写入，读的是旧文件，**自己骗自己** |

**一句话总结思路转变**：从「把对象丢给流，流自己会搞定」→「**序列化是一份跨进程的协议：类结构、版本号、流的开关顺序，哪一样对不上都读不回来**」。

## 三、逐个问题记录

### 问题 1：`Student` 没实现 `Serializable`，`writeObject` 直接抛异常

**代码**

```java
public class Student {          // ← 没有 implements Serializable
    private Integer id;
    private String name;
    // ...
}
```

```java
Student student = new Student(1, "doro", 2, "114514");
try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("student.dat"))) {
    oos.writeObject(student);   // 这一行抛异常
} catch (IOException e) {
    throw new RuntimeException(e);
}
```

**报错（实测）**

```
Exception in thread "main" java.lang.RuntimeException: java.io.NotSerializableException: Student
	at Main.main(Main.java:7)
Caused by: java.io.NotSerializableException: Student
	at java.base/java.io.ObjectOutputStream.writeObject0(ObjectOutputStream.java:1087)
	at java.base/java.io.ObjectOutputStream.writeObject(ObjectOutputStream.java:327)
	at Main.main(Main.java:6)
```

**原因**

`Serializable` 是一个**标记接口（marker interface）**——里面一个方法都没有。它不提供任何能力，只表示「这个类的作者授权 JVM 把它压成字节」。

所以它是**开关**，不是**实现**。不写 `implements Serializable`，`writeObject` 就拒绝干活。而且这个「开关」是**递归生效**的：类里的引用类型字段（比如 `Integer`、`String`）也必须是可序列化的，否则报错会发生在「外层对象已经写了一半」的时候。

**解决**

```java
public class Student implements Serializable {
```

**收获**：空接口不代表没用。`Serializable` 这类接口的作用是**给运行时看的一张许可证**，不是给调用者调的方法。

### 问题 2：`src` 下那个 **0 字节** 的 `student.dat` 是哪来的

**现象**

`05/src/student.dat` 存在，但**大小是 0**，时间戳停在 13:38，之后再没变过。而程序看起来"跑过"。

**排查过程**

先在整个仓库里找所有 `.dat`：

| 位置 | 大小 | 时间 |
| --- | --- | --- |
| `05/src/student.dat` | **0 字节** | 13:38 |
| `out/production/05/student.dat` | **0 字节** | 13:38 |
| `D:\java\2\student.dat`（仓库根目录） | **213 字节** | 14:10 |

三个文件！真正写成功的是**仓库根目录**那个。`src` 下那个是从 13:38 就躺在那里、再没被碰过的**旧残留**（mtime 一直不变就是证据）。

**0 字节到底意味着什么（实测验证）**

我写了两种极端情况单独跑，看文件落地结果：

```java
try (FileOutputStream fos = new FileOutputStream("a.dat")) { }        // 只建文件，什么都不写
try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("b.dat"))) { }   // 只构造对象流，空体
```

```
a.dat   0 字节
b.dat   4 字节
```

**这个对比是关键**：

- `new FileOutputStream(...)` 在**构造的那一刻**就把文件创建出来（存在则截断为 0 字节），跟后面写不写没关系。
- 而 `ObjectOutputStream` **一构造就写了 4 字节**（流头 `ac ed 00 05`），立刻落盘。

所以 **0 字节比 4 字节更"早"**：它说明 `FileOutputStream` 建完文件之后，`ObjectOutputStream` **根本没构造成功**，或者进程在那一行之前就停了。文件存在 ≠ 流工作过。

**顺带纠正一个我自己的错误认知**

我原本以为「写入失败会留下 0 字节」。实测是**错的**：

```
写入失败（Student 未实现 Serializable，try-with-resources）→ 文件 1216 字节
```

`ObjectOutputStream` 抛 `NotSerializableException` 时，会顺手**把异常对象本身也序列化写进流里**（`writeFatalException`），并且 flush 一次。所以磁盘上留下的不是空文件，而是一段 1KB 多、装着异常信息的字节流。

**结论**：0 字节 = 连流头那 4 个字节都没写出去，也就是对象流**压根没开始工作**；写入失败反而会留下 1KB 左右的"垃圾字节"。

**收获**

- 磁盘上的文件大小是一份**执行日志**：0 字节、4 字节、1KB、213 字节，各自对应流程走到哪一步断的。
- 排查时**先在整个仓库范围内找同名文件**，别只盯着眼前那一个——它可能根本不是这次的产物。

### 问题 3：文件没写在我以为的地方——相对路径跟着**工作目录**跑

**现象**

程序跑完，`05/src/` 下毫无动静，反而在**仓库根目录** `D:\java\2\` 冒出来一个 213 字节的 `student.dat`。

**原因**

`new FileOutputStream("student.dat")` 用的是**相对路径**，相对的是**进程的工作目录（working directory）**，**不是源码所在的目录**。

- 13:38 那次运行，工作目录是 `out/production/05`（IDEA 的编译输出目录）
- 14:10 那次运行，工作目录是 `D:\java\2`

所以同一个 `new FileOutputStream("student.dat")`，两次运行写到了**两个完全不同的地方**，而 `src/` 下那个老文件一直没人管。

**解决**

先把它打印出来，别再靠猜：

```java
System.out.println(new File("student.dat").getAbsolutePath());
```

再把工作目录钉死：IDEA 里 Run → Edit Configurations → `Working directory` 设成 `$MODULE_WORKING_DIR$`，文件就规规矩矩生成在 `05/` 下了。

**收获**：**相对路径是相对"谁在跑"，不是相对"代码在哪"。** 只要程序里出现相对路径，第一件事就该是把绝对路径打出来看一眼。

### 问题 4：`Student.dat` ≠ `student.dat`

**代码**

```java
new FileOutputStream("student.dat")   // 第 6 行：小写 s
new FileInputStream("Student.dat")    // 第 12 行：大写 S ← 对不上
```

**现象**

在 Windows 上**跑得通**，什么都没报。原因是 **NTFS 默认不区分大小写**——`Student.dat` 被系统"宽容"地匹配到了刚写出来的 `student.dat`。

证据是 `ls -la student.dat Student.dat` 会把**同一个文件**列出来两遍，大小和时间戳一模一样。

**换到 Linux / macOS 会怎样**（本机无 WSL/Linux 环境，这一条是推演，非实测）

那里大小写敏感，目录里只有 `student.dat`，程序会老老实实去找一个字面叫 `Student.dat` 的文件，找不到就抛：

```
java.io.FileNotFoundException: Student.dat (No such file or directory)
```

**解决**：统一成小写 `student.dat`。

**收获**：**Windows 上的"跑得通"不能当证据。** 文件名当字符串看，大小写本身就是一个应该对齐的标识符。

### 问题 5：`serialVersionUID`——从编译器算的大数，到我写死的 `1`

**现象**

不写 `serialVersionUID` 时，程序能跑，看不出任何问题。

**把字节流 dump 出来看**

```
ac ed 00 05                                      ← 魔数 ACED + 版本 5
73 72 00 07 53 74 75 64 65 6e 74                 ← 0x73=TC_OBJECT 0x72=TC_CLASSDESC 类名"Student"
87 44 6f 76 c7 f6 4e 02                          ← serialVersionUID（编译器自动算的）
```

那个 `87 44 6f 76 c7 f6 4e 02` 就是我**没写**时编译器替我算出来的**结构哈希**——它由类名、接口、字段、方法签名一起算出来。

**报错（实测）**

给 `Student` 加一个字段、不改版本号，重新编译后再读旧文件：

```
java.io.InvalidClassException: Student; local class incompatible: stream classdesc serialVersionUID = 3902974409148962811, local class serialVersionUID = -5180524765698530587
	at java.base/java.io.ObjectStreamClass.initNonProxy(ObjectStreamClass.java:496)
	at java.base/java.io.ObjectInputStream.readNonProxyDesc(ObjectInputStream.java:1927)
	at java.base/java.io.ObjectInputStream.readClassDesc(ObjectInputStream.java:1785)
	at java.base/java.io.ObjectInputStream.readOrdinaryObject(ObjectInputStream.java:2101)
	at java.base/java.io.ObjectInputStream.readObject0(ObjectInputStream.java:1620)
```

两边的号一对比，JVM 直接拒绝——**旧文件成了废纸**。

**解决**

```java
@Serial
private static final long serialVersionUID = 1L;
```

写死之后重新看字节流，那一段变成：

```
00 00 00 00 00 00 00 01                          ← 就是我写死的 1L
```

**验证：写死版本号之后，加字段是兼容的**

刚才那个 213 字节的旧文件，是 `Student` **还没有 `test` 字段**时写的。给类加上字段、版本号保持 `1L`，再读旧文件：

```
Student{id=1, name='doro', gender=2, phone='114514'}
```

**读回来了。** 流里有而本地类没有的字段被忽略，本地类新增的字段读出默认值——这就是「只要版本号一致，字段增删算兼容」。

**收获**：`serialVersionUID` 是**序列化协议里的版本号**。不写死，就等于把版本号交给编译器按类结构随机生成——任何一次无心的字段改动都会让历史数据作废。

### 问题 6（附带）：`transient` 和 `static` 不参与序列化

顺手验一下这两条规则：

```java
private transient String phone;
```

```
Student{id=1, phone=null}
```

`phone` 读回来是 `null`——它**根本没被写进流**，反序列化后拿到的只是默认值。`static` 字段同理（属于类不属于对象）。要跳过的字段挂 `transient`，密码、缓存、不可序列化的引用都该挂。

---

### 问题 7（附带）：反序列化**不走构造方法**

这一点最反直觉：对象不是被 `new` 出来的，而是 JVM 直接从字节流里"拼"出来的，**`Student` 的构造器一次都不会执行**。

推论：写在构造方法里的校验、字段初始值，反序列化时全都被绕过——这也正是 Java 原生反序列化成为一系列 RCE 漏洞源头的原因：攻击者构造一段字节流，就能凭空造出对象，跳过所有初始化校验。

所以生产代码里，**永远不要反序列化不可信来源的数据**。

---

### 问题 8（附带）：`@Serial` 注解

```java
import java.io.Serial;

@Serial
private static final long serialVersionUID = 1L;
```

`@Serial`（JDK 14+）是给编译器看的标记注解：如果**你把它贴在错误的东西上**（比如贴在一个普通字段上、或 `serialVersionUID` 写错类型写成了 `int`），编译期就会报警告。它不影响运行，属于"写错了能早点发现"的保险。

---

### 问题 9（附带）：`Student` 里有个没人赋值的 `test` 字段

```java
private String test;   // 构造器里没有它，setter 也没有
```

这个字段从头到尾**没有任何地方赋值**，永远是 `null`；`toString()` 里也没打印它，所以肉眼完全看不出来。

它不影响本题运行（版本号写死了，兼容），但属于需要说明的残留——**要么删掉，要么在构造器里给它赋值**。留着不加说明，读代码的人会以为漏写了什么。

---

### 问题 10（附带）：调试时把写入那段注释掉了

```java
//        try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("student.dat"))) {
//            oos.writeObject(student);
//        }
```

调试读取逻辑时这么干很方便，但有个陷阱：**改了类结构之后如果忘了放开注释，程序读的还是上一个旧文件，输出一切正常——于是误以为改动没问题**。

序列化调试的铁律：**写和读一定成对跑**，否则你验证的是历史数据，不是当前代码。

（最后定稿时写入段已经放开，写和读是成对跑的，见「四、最终代码」。）

### 问题 11（附带）：`try (...)){` 后面多了一个分号

```java
try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("student.dat"));){
    oos.writeObject(student);
}catch (IOException e){ ... }
//                                          ↑ 这个分号是空语句
```

`try` 块后面直接跟一个 `;`，在 Java 里是一条**空语句（empty statement）**——合法、无害，什么都不做。编译器不会报错，程序行为也完全一样。

留着它没什么坏处，但读代码的人会在那儿停一下："这个分号是干什么的？"——所有需要读者停下来想"这是不是笔误"的东西，都值得删掉。

**解决**：去掉那个 `;`，写成 `try (...) {` 即可。

**收获**：Java 允许空语句（`for (;;);` 这种就靠它），所以多余的 `;` 不会报错。**"能编译"不等于"该留着"。**

## 四、最终代码

### `Student.java`

```java
import java.io.Serial;
import java.io.Serializable;

public class Student implements Serializable {
    private Integer id;
    private String name;
    private Integer gender; //1表示男性 2表示女性
    private String phone;
    private String test;

    @Serial
    private static final long serialVersionUID = 1L;

    public Student(Integer id, String name, Integer gender, String phone) {
        this.id = id;
        this.name = name;
        this.gender = gender;
        this.phone = phone;
    }

    public Integer getId() { return id; }
    public void setId(Integer id) { this.id = id; }

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }

    public Integer getGender() { return gender; }
    public void setGender(Integer gender) { this.gender = gender; }

    public String getPhone() { return phone; }
    public void setPhone(String phone) { this.phone = phone; }

    @Override
    public String toString() {
        return "Student{" +
                "id=" + id +
                ", name='" + name + '\'' +
                ", gender=" + gender +
                ", phone='" + phone + '\'' +
                '}';
    }
}
```

### `Main.java`

```java
import java.io.*;

public class Main {
    static void main(String[] args) {
        Student student = new Student(1, "doro", 2, "114514");
        try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("student.dat"));){
            oos.writeObject(student);
        }catch (IOException e){
            throw new RuntimeException(e);
        }

        try(ObjectInputStream ois =new ObjectInputStream(new FileInputStream("student.dat"))){
            Student s= (Student) ois.readObject();
            System.out.println(s);
        } catch (IOException | ClassNotFoundException e) {
            throw new RuntimeException(e);
        }

    }
}
```

**说明**：上面这段就是仓库里 `05/src/Main.java` 的实际内容（含「问题 11」提到的那个多余分号）。两条路径都是 `student.dat`——相对路径跟着**工作目录**跑，所以运行时得先站在 `05/` 下（IDEA 里对应把运行配置的 Working directory 设成模块根 `05`）。

## 五、运行与验证

```
Student{id=1, name='doro', gender=2, phone='114514'}
```

同时验证了三件事：

1. 生成的 `student.dat` 是 **226 字节**——不再是 0 字节，说明对象流真的工作了（比加 `test` 字段之前的 213 字节多了 13 字节：多一个字段，类描述里就多一段）
2. 字节流开头是 `ac ed 00 05`，类描述段里写着文件名 `Student` 和版本号 `00 00 00 00 00 00 00 01`
3. 给 `Student` **新增字段后**，用 `serialVersionUID = 1L` 仍然读得回旧文件

## 六、概念小结

| 概念 | 一句话记住 |
| --- | --- |
| 序列化 / 反序列化 | 对象 ↔ 字节序列，为的是跨进程、跨时间保存对象 |
| `Serializable` | **标记接口**，没有方法；作用是"授权"而非"提供能力"。不实现就抛 `NotSerializableException` |
| 字段也要可序列化 | 引用类型的字段同样得实现 `Serializable`，否则报错发生在写了一半的时候 |
| `FileOutputStream` 的构造 | **一 new 出来就创建/截断文件**，此时还没有任何内容 |
| 0 字节 vs 4 字节 | 只建 `FileOutputStream` → 0 字节；一构造 `ObjectOutputStream` 就落 4 字节流头。**0 字节说明对象流压根没工作** |
| 写入失败 ≠ 空文件 | `ObjectOutputStream` 会把 `NotSerializableException` **本身**写进流里并 flush，实测留下 1216 字节 |
| 相对路径 | 相对**工作目录**，不是源码目录；动手前先 `getAbsolutePath()` 打出来 |
| 文件名大小写 | Windows 不区分（侥幸能跑），Linux/macOS 区分（直接 `FileNotFoundException`） |
| `serialVersionUID` | 序列化协议的版本号。不写就由编译器按类结构算，**改一个字段就作废历史数据** |
| `transient` / `static` | 不参与序列化，读回来是默认值 |
| 反序列化与构造器 | **不走构造方法**，对象直接从字节流拼出来；也因此成为安全漏洞源头，别反序列化不可信数据 |
| `@Serial` | JDK 14+ 的编译期检查注解，贴错了会报警告 |
