# 微光2026招新-Web后端-05 · 名单排序 · 思考过程与问题记录

> 记录实现「读取名单 → 去除多余空白 → 排序 → 写出新文件」这道题时，从写第一行到跑通的全过程：想过什么、错在哪、最后怎么改对的。
>
> 环境：JDK 27 / Windows 11
>
> 说明：本文的代码和输出均来自 2026-10-01 那次实现过程，写这份记录时又抽查复现了一遍。「最终代码」一节即仓库中 `05/src/Name.java` 的实际内容。

---

## 一、题目要求

读入 `name.txt`（每行一个名字，带不定长的前导空格，中间夹着空行），把它整理后写到 `name_sorted.txt`：

- 去掉每行前导/尾随空格
- 丢掉空行
- 按 **Unicode** 排序

---

## 二、整体思路的演变

| 阶段 | 我当时的想法 | 后来发现的问题 |
| --- | --- | --- |
| 1 | 用 `String[30]` 一次性把整份名单装下来 | 长度写死；数组尾巴留了一堆 `null` |
| 2 | 调 `Arrays.stream(str).sorted();` 排序 | **静默空转**——`sorted()` 是中间操作，返回值还被丢掉了，JVM 一步没做 |
| 3 | 用 `str[i].trim();` 去空白 | `String` 不可变，返回值扔了，空格原封不动 |
| 4 | 改用 `List<String>` + `str.sort(Comparator.naturalOrder())` | ✅ 对了 |
| 5 | 输出流的 `OutputStreamWriter` 没写 charset | JDK 27 因 JEP 400 恰好是 UTF-8；换老 JDK 会变 GBK |
| 6 | 判空用 `l.isEmpty()`，判在 `trim()` 之前 | 纯空格行 `"   "` 的 `isEmpty()` 是 `false`，会被 trim 成空串收进来 |
| 7 | 用 `forEach` 写文件，里面 `throw new RuntimeException` | 外层 `catch (IOException)` **抓不到** RuntimeException，错误处理形同虚设 |

**一句话总结思路转变**：从「代码能编译、程序能跑完 = 对了」→「**输出必须能证明它真的干活了**」。

**这道题最值得记的一点**：它**从头到尾没有任何报错**。程序正常退出，输出文件也正常生成——它只是**什么都没做**。

## 三、逐个问题记录

### 问题 1：程序跑通了，但排序根本没生效（**零报错**）

**现象**

程序编译通过、运行无异常、`name_sorted.txt` 也生成了，看起来一切正常。

**怎么发现的**

拿输入和输出做了一次 `diff`：

```
$ diff name.txt name_sorted.txt
21c21
< 杨二十
\ No newline at end of file
---
> 杨二十
```

**除了末尾多一个换行，190 个字节完全相同**——输出就是把输入原样抄了一遍，一个都没排。

**当时的代码**

```java
String[] str = new String[30];
int i = 0;
while ((str[i] = bufferedReader.readLine()) != null) {
    str[i].trim();
    i++;
}
int j = 0;
Arrays.stream(str).sorted();          // ← 第 16 行
while (j < i) {
    bufferedWriter.write(str[j]);
    bufferedWriter.newLine();
    j++;
}
```

**原因（这一行错在两个地方，而且是叠加的）**

`Arrays.stream(str).sorted();` 拆开看：

1. **`stream()` 和 `sorted()` 都是中间操作（intermediate operation）**。中间操作只是往流水线上"挂"了一步，**流水线只有遇到终结操作（terminal operation，如 `forEach` / `collect` / `toArray` / `count`）才会真正跑起来**。这里从头到尾没有终结操作 → **整个流水线一条语句都没执行**。
2. **就算它执行了，也不会改原数组**。`Stream.sorted()` 返回的是**一个新的流**，不修改数据源。而这里的返回值连接都没接，直接丢掉了。

两处错误**各自都足以让排序不发生**，叠在一起，结果就是「这行代码等于没写」。

**对照：正确的两种写法**

```java
Arrays.sort(str, 0, i);              // 原地排序，返回 void —— "就地改"
List<String> list = ...;
list.sort(Comparator.naturalOrder()); // List.sort 也是原地排序
```

```java
String[] sorted = Arrays.stream(str).sorted().toArray(String[]::new);  // 流式：必须接住返回值
```

**区别一句话**：`Arrays.sort` / `List.sort` 是「**就地改**」，返回 `void`，改的就是你传进去的那个东西；`stream().sorted()` 是「**另起一份**」，必须把返回值接住。把「另起一份」的写法用在「就地改」的期待上，就是这次的坑。

**验证方式**

写了个只读不写的小程序单独验这两句：

```
调完 sorted() 之后，数组 = [  张三, 李四, ,  王五]      ← 原封不动，连空格都在
调完 trim()   之后，str[0] = [  张三]                   ← 同样没变
```

**收获**：**编译通过 ≠ 逻辑生效。** 一道没有报错的题，比一道报错的题危险得多——报错会强迫你看，静默失败不会。这道题唯一的"报警器"是 `diff`，所以我后来养成了一个习惯：**凡是写文件的程序，写完都要拿输入和输出对一次。**

### 问题 2：`str[i].trim();` —— 去空白也白去了

**代码**

```java
while ((str[i] = bufferedReader.readLine()) != null) {
    str[i].trim();          // ← 返回值没人接
    i++;
}
```

**原因**

`String` 是**不可变（immutable）**的。`trim()` 不会修改 `str[i]` 本身，它返回的是**一个新的字符串**。不接返回值，等于把好不容易去完空白的那个新串直接扔了，原串纹丝不动。

上面那段验证输出里写得很清楚：

```
调完 trim() 之后，str[0] = [  张三]      ← 前导空格还在
```

**解决**

```java
String trim = l.trim();     // 接住
str.add(trim);
```

**收获**：`String` 的方法（`trim` / `substring` / `replace` / `toUpperCase`…）**全都是返回新串**。这是 Java 字符串最基础也最容易忘的一条。同类还有个 `StringBuilder`，它才是就地修改的。

### 问题 3：`String[30]` 的尾巴，就是那个「结尾的 null」

**现象**

我一度以为输出文件「结尾是 null」。

**原因**

```java
String[] str = new String[30];    // 长度写死 30
```

实际只填了 21 行，**`str[21]` 到 `str[29]` 全是 `null`**。

当时没爆，是因为排序那句空转了、写出循环也只用 `j < i` 卡住了范围。但只要排序一接上（比如写成 `Arrays.sort(str)`），`null` 混进比较就会立刻：

```
java.lang.NullPointerException
```

自然序比较器不接受 `null`。

**解决**

换成 `List<String>`（`ArrayList`），长度天然跟着内容走，**尾巴上的 null 从根上消失**。

**收获**：**数组的"容量"和"内容长度"是两回事**。写死长度的数组一定会在某个地方逼你手工维护"实际用到几个"，而这个数迟早会和真实长度对不上。装不定长数据，直接用 `List`。

### 问题 4：`isEmpty()` 判在 `trim()` 之前（隐患，当时数据没触发）

**代码**

```java
if (!l.isEmpty()) {
    String trim = l.trim();
    str.add(trim);
}
```

**问题**

对**纯空格行** `"   "` 来说，`isEmpty()` 返回的是 `false`（它非空，只是全是空格），于是这行会被放进去、`trim()` 之后变成一个**空字符串**，混进名单里。

当前这份 `name.txt` 的空行是真·空行（`""`），所以没触发。但只要哪天有一行是「空格 + 空格」，就中招。

**解决**（仓库里已经是这版）

```java
if (!l.isBlank()) {          // isBlank()：全是空白字符也算"空"
    String trim = l.trim();
    str.add(trim);
}
```

`isBlank()`（JDK 11+）和 `isEmpty()` 的区别：`" "` 对前者是 `true`，对后者是 `false`。

**收获**：**判空和去空白有先后顺序**——要么先 `trim` 再判空，要么直接用 `isBlank()` 一步到位。

### 问题 5：输出流漏了 charset（隐患，JDK 27 上恰好没事）

**代码**

```java
new OutputStreamWriter(new FileOutputStream("name_sorted.txt"))    // ← 没写 charset
```

输入流规规矩矩写了 `StandardCharsets.UTF_8`，**输出流漏了**。

**为什么当时没出事**

不写 charset，`OutputStreamWriter` 用**平台默认编码**。JDK 18 起（JEP 400）平台默认编码被统一成 UTF-8，所以在 JDK 27 上恰好也是 UTF-8，看着一切正常。

换到 JDK 8 / 11 / 17，默认编码是 GBK，写出来就是乱码——**同一份代码，换个 JDK 就坏**。

**解决**（仓库里已经是这版）

```java
new OutputStreamWriter(new FileOutputStream("name_sorted.txt"), StandardCharsets.UTF_8)
```

**收获**：**读写两端都要显式指定编码**，别依赖"平台默认"。这是那种「在我这儿好好的、到评测机上就炸」的经典坑。

### 问题 6：`forEach` 里 `throw new RuntimeException` —— 外层 catch 抓不到（隐患，当时数据没触发）

**代码（16:44 那版）**

```java
try (BufferedReader ...; BufferedWriter ...) {
    ...
    str.forEach(line -> {
        try {
            bufferedWriter.write(line);
            bufferedWriter.newLine();
        } catch (IOException e) {
            throw new RuntimeException(e);    // ← 包成 RuntimeException 再扔
        }
    });
} catch (IOException e) {                      // ← 这里抓不到 RuntimeException
    e.printStackTrace();
}
```

**问题**

外层 `catch (IOException e)` 是**编译期检查异常**的处理器，**它抓不住 `RuntimeException`**。真出 IO 错误时，异常会直接穿透外层 try 抛到 `main` 外面，错误处理**形同虚设**。

**解决**（仓库里已经是这版）

改回普通 `for` 循环——循环体本来就在 try 块里，`IOException` 能正常被外层接住，根本不需要 lambda 里那层 catch：

```java
for (String line : str) {
    bufferedWriter.write(line);
    bufferedWriter.newLine();
}
```

**收获**：lambda 里做 IO 很别扭，因为函数式接口（`Consumer`）**不允许抛检查异常**，逼着你 try-catch 或包装。这里 `forEach` 并没有带来任何好处，用普通 `for` 反而更干净。**别为了"看起来函数式"而用流。**

### 问题 7：排序规则——Unicode 码位序，不是拼音序

这是题目明确要求的，也是这道题最"反直觉"的结果。同样 18 个名字，两种排序规则给出的顺序完全不同：

```
① 默认（Unicode 码位序）:
   [冯十三, 卫十六, 吴十, 周八, 孙七, 张三, 李四, 杨二十, 沈十八, 王五, 王十二,
    蒋十七, 褚十五, 赵六, 郑十一, 钱九, 陈十四, 韩十九]

② Collator(Locale.CHINA)（拼音序）:
   [陈十四, 冯十三, 韩十九, 蒋十七, 李四, 钱九, 沈十八, 孙七, 王十二, 王五,
    卫十六, 吴十, 杨二十, 张三, 赵六, 郑十一, 周八, 褚十五]
```

注意 ① 里 `冯十三` 排在最前面——`冯`(U+51AF) 的码位比 `卫`(U+536B) 小，纯粹是这个原因，和读音、笔画都没关系。**默认的 `String.compareTo` 比的是 UTF-16 码元大小。**

本题按题目要求用的是 ①（`Comparator.naturalOrder()`）。如果哪天题目要拼音序：

```java
Collator.getInstance(Locale.CHINA)
```

它本身就是一个 `Comparator<Object>`，可以直接传进 `sort()`。

**收获**：**"按 Unicode 排序"和"按拼音排序"是两回事**，做题前先看清题目要哪个。

## 四、最终代码

```java
import java.io.*;
import java.nio.charset.StandardCharsets;
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class Name {
    static void main(String[] args) {
        try (BufferedReader bufferedReader = new BufferedReader(
                 new InputStreamReader(new FileInputStream("name.txt"), StandardCharsets.UTF_8));
             BufferedWriter bufferedWriter = new BufferedWriter(
                 new OutputStreamWriter(new FileOutputStream("name_sorted.txt"), StandardCharsets.UTF_8))) {

            List<String> str = new ArrayList<>();
            String l;
            while ((l = bufferedReader.readLine()) != null) {
                if (!l.isBlank()) {
                    String trim = l.trim();
                    str.add(trim);
                }
            }
            str.sort(Comparator.naturalOrder());
            for (String line : str) {
                bufferedWriter.write(line);
                bufferedWriter.newLine();
            }

        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}
```

（仓库里这份就是最终版；上面问题 4、问题 6 提到的两个隐患，现在都已经改掉了。）

## 五、运行与验证

输入 `name.txt`：21 行（18 个名字 + 3 个空行），**UTF-8 + CRLF**，多行带前导空格，例如第 1 行是 `␣␣张三`。

输出 `name_sorted.txt`：**18 行**，顺序为

```
冯十三
卫十六
吴十
周八
孙七
张三
李四
杨二十
沈十八
王五
王十二
蒋十七
褚十五
赵六
郑十一
钱九
陈十四
韩十九
```

验证点：

1. 空行被**丢掉**了（21 行进 → 18 行出）
2. 前导空格被**去掉了**——输出文件开头 12 个字节是 `e5 86 af e5 8d 81 e4 b8 89 0d 0a e5`，即 `冯十三` 直接顶到最前面，没有空格

4. 只有 `name.txt` 和排序后的 `name_sorted.txt` 名称一致

## 六、概念小结

| 概念 | 一句话记住 |
| --- | --- |
| 静默失败 | 编译通过、运行无异常、文件也生成了，**但逻辑根本没执行**。靠 `diff` 输入输出才能发现 |
| 中间操作 vs 终结操作 | `stream()` / `sorted()` 只是挂流水线；**没有 `forEach`/`collect`/`toArray` 就一步都不跑** |
| 就地改 vs 另起一份 | `Arrays.sort` / `List.sort` 就地改、返回 `void`；`stream().sorted()` 返回新流，**必须接住返回值** |
| `String` 不可变 | `trim()` / `substring()` / `replace()` 全都返回**新串**，不接返回值等于没调用 |
| 数组的容量 ≠ 长度 | `new String[30]` 装 21 条，尾巴 9 个 `null`；装不定长数据用 `List` |
| `isEmpty()` vs `isBlank()` | `"   "` 对前者 `false`、对后者 `true`；判空要么放在 `trim` 之后，要么直接用 `isBlank()` |
| 编码要两端都写 | `OutputStreamWriter` 不写 charset 就用平台默认；JDK 18+ 恰好是 UTF-8，老 JDK 是 GBK——**换个 JDK 就炸** |
| lambda 与检查异常 | 函数式接口不能抛 `IOException`，逼你包装；外层 `catch (IOException)` **抓不住** `RuntimeException` |
| Unicode 序 vs 拼音序 | 默认 `compareTo` 比的是码位（`冯` U+51AF 排在 `卫` U+536B 前）；要拼音序用 `Collator.getInstance(Locale.CHINA)` |
