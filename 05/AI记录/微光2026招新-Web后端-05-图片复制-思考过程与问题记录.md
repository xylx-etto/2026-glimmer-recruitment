## 一、题目要求

用字节流（`FileInputStream` / `FileOutputStream`）把 `doro.jpg` 复制一份。

---

## 二、整体思路的演变

| 阶段 | 我当时的想法 | 后来发现的问题 |
| --- | --- | --- |
| 1 | `new FileInputStream("src/doro.jpg")` | 找不到文件 |
| 2 | 改成 `"doro.jpg"` | **还是找不到**——两次失败其实是同一个原因，我一直以为是在试不同路径 |
| 3 | `new FileOutputStream()` 不传参 | 编译不过：`FileOutputStream` 没有无参构造器 |
| 4 | 输出流开在 `while` 里面 | 每轮 new 一次、默认 `append=false`，反复把文件截断 |
| 5 | `write(bytes)` 整个缓冲区写出去 | 副本比原图**大 417 字节**，前面全对、尾巴是脏数据 |
| 6 | 输出流提到 try 的括号里 + `write(bytes, 0, len)` | ✅ 逐字节一致 |

**一句话总结思路转变**：从「把对象丢给流、流自己会搞定」→「**流是状态机：往哪儿写、开几次、写多少，每一步都得自己说清楚**」。

## 三、逐个问题记录

### 问题 1：同样的「找不到文件」，我换了两遍路径都没对

**现象**

第一次写 `"src/doro.jpg"`，找不到；改成 `"doro.jpg"`，**还是找不到**。我以为是路径试错了，其实两次错的是同一件事。

**报错原文（复现输出）**

```
java.io.FileNotFoundException: doro.jpg (系统找不到指定的文件。)
	at java.base/java.io.FileInputStream.open0(Native Method)
	at java.base/java.io.FileInputStream.open(FileInputStream.java:185)
	at java.base/java.io.FileInputStream.<init>(FileInputStream.java:139)
	at java.base/java.io.FileInputStream.<init>(FileInputStream.java:109)
	at A.main(A.java:4)
```

（`A.java` 是复现时用的最小文件；堆栈里 `open0 → open → <init>` 那几层和真实情况完全一样。）

**原因**

Java 的相对路径，相对的是 **JVM 进程的工作目录（`user.dir`）**，**不是 `.java` 源文件所在的目录**。而 IDEA 默认的工作目录是**项目根 `D:\java\2`**。

同一份代码、只换工作目录跑两次：

```
--- 从 D:/java/2 运行（IDEA 默认工作目录）---
java.io.FileNotFoundException: doro.jpg (系统找不到指定的文件。)

--- 从 05/src 运行 ---
104031
```

（`104031` 正是 `doro.jpg` 的字节数——文件找到了，读出来了。）

对着这个结果就能看清两个写法的成立条件：

| 写法 | 只有在工作目录是…时才成立 |
| --- | --- |
| `"src/doro.jpg"` | `05/` |
| `"doro.jpg"` | `05/src/` |

**我两次都失败，是因为我在换字符串，而问题在工作目录。** 光靠试路径，试一百次也试不出来——得先知道自己在哪儿。

**解决**

```java
new FileInputStream("05/src/doro.jpg")
```

更稳的习惯是**先把它打印出来**，别猜：

```java
System.out.println(new File("doro.jpg").getAbsolutePath());
```

**收获**：**相对路径是相对「谁在跑」，不是相对「代码在哪」。** 只要程序里出现相对路径，第一件事就该是把绝对路径打出来看一眼。

### 问题 2：`new FileOutputStream()` —— 它根本没有无参构造器

**代码**

```java
try (FileOutputStream fileOutputStream = new FileOutputStream()) {
    fileOutputStream.write(bytes);
}
```

**报错原文（复现输出）**

```
B.java:4: 错误: 对于FileOutputStream(没有参数), 找不到合适的构造器
        try (FileOutputStream fos = new FileOutputStream()) { }
                                    ^
    构造器 FileOutputStream.FileOutputStream(String)不适用
      (实际参数列表和形式参数列表长度不同)
    构造器 FileOutputStream.FileOutputStream(String,boolean)不适用
      (实际参数列表和形式参数列表长度不同)
    构造器 FileOutputStream.FileOutputStream(File)不适用
      (实际参数列表和形式参数列表长度不同)
    构造器 FileOutputStream.FileOutputStream(File,boolean)不适用
      (实际参数列表和形式参数列表长度不同)
    构造器 FileOutputStream.FileOutputStream(FileDescriptor)不适用
      (实际参数列表和形式参数列表长度不同)
1 个错误
```

**原因**

编译器把 5 个候选构造器全列出来了，**每一个都要一个落点参数**——输出流必须知道「写到哪里去」。这不是重载挑选失败，而是**这一类构造器压根不存在**。

对比一下输入流：`new FileInputStream("...")` 我们本来就会给它一个路径，因为"读哪个文件"是明确的。到了输出流，很容易顺手写个空的——**因为「复制出来的文件叫什么」这件事，我当时根本没想过**。写出来才发现，程序缺的不是语法，是一条我没做的决定。

**解决**

给它一个落点：

```java
new FileOutputStream("doro_copy.jpg")
```

输出文件名 `doro_copy.jpg` 就是这么定下来的——**总得有个地方让数据落下去**。

**收获**：报错信息里那 5 个候选构造器，其实是在提醒你「这个东西**必须**有个目标」。设计 API 的人用「不给无参构造器」的方式，逼你想清楚这件事。

### 问题 3：输出流开在了 `while` 里面

**代码**

```java
while (fileInputStream.read(bytes) != -1) {
    try (FileOutputStream fileOutputStream = new FileOutputStream("...")) {   // ← 每轮都 new
        fileOutputStream.write(bytes);
    }
}
```

**问题**

输出流每轮循环都新建、每轮结束又关闭，而 `FileOutputStream` 默认 `append = false`——**每次打开都会先把文件截断成 0 字节**。

等于前面写进去的内容，全被下一轮自己清掉了。最后只剩最后一轮那一块数据。所谓「复制」，变成了「只保留最后 1KB」。

**解决**

输出流和输入流一样，**开到 try 的括号里**，整个复制过程只开一次：

```java
try (FileInputStream fileInputStream = new FileInputStream("doro.jpg");
     FileOutputStream fileOutputStream = new FileOutputStream("doro_copy.jpg")) {
    ...
}
```

**收获**：**流的生命周期要跟它的语义对齐。** 一个输入流、一个输出流，代表的是「一次完整的读写会话」，就该活在整个循环外面。放进循环里，等于每写一块就重新开始一次会话。

顺带一个反直觉点：**`try` 括号里的资源是在「`try` 块整体结束时」才关的**，不是每轮循环关一次——这正好是这里想要的行为。

### 问题 4：`write(bytes)` —— 复制出来的文件比原图大（复现）

**代码**

```java
while ((len = fileInputStream.read(bytes)) != -1) {
    fileOutputStream.write(bytes);      // ← 把整个 1024 字节缓冲区都写出去
}
```

**实测结果**

```
104031  doro.jpg      原图
104448  full.bin      write(bytes)      写整个缓冲区
104031  proper.bin    write(bytes,0,len)
```

```
cmp: EOF on 'doro.jpg' after byte 104031
→ full.bin 与原图不一致，尾部多出 417 字节
```

**原因**

`read(bytes)` 的返回值 `len` 是**这一轮实际读到了几个字节**，而 `bytes` 这个数组是**反复复用的**。

最后一轮只读到 **607** 字节，数组里却还留着**上一轮**的 1024 个字节。`write(bytes)` 不看 `len`，把整整 1024 个都写了出去：

```
多写的 = 1024 - 607 = 417 字节
总写入 = 1024 × 102 = 104448     （真实只有 104031）
```

**这个 bug 最阴的地方**：`cmp` 报的是 "EOF on doro.jpg"——**文件前面全对**，只是尾巴多一截。用图片查看器打开，图大概率**还能正常显示**（JPEG 的 EOI 结束标记还在前面），肉眼完全看不出问题。只有逐字节比对才暴露出来。

而那多出来的 417 字节**不是随机垃圾**，是这张图开头那 417 个字节的副本——缓冲区没截断，写出去的就是上一轮的真实数据。

**解决**

```java
fileOutputStream.write(bytes, 0, len);      // 只写实际读到的 len 个字节
```

**收获**：**`read` 的返回值必须接住，而且必须一路传到 `write`。** 「文件比预期大一点」这类怪现象，八成就是缓冲区复用 + 忘了截断。

### 问题 5：`available()` 不是「文件长度」

我一度用 `fileInputStream.available()` 打印出 `104031`，正好等于 `doro.jpg` 的大小，就想拿它当文件长度用。

它真正返回的是「**在不阻塞的情况下，估计还能读到多少字节**」——是个**估计值**。对本地普通文件它恰好等于剩余大小，所以看着像；换到网络流、管道、压缩流，含义完全不同。

**正确做法**：想知道文件多大就 `new File(path).length()`；读数据一律用 `read()` 的循环，**不要拿 `available()` 当循环上界**。

### 问题 6（附带）：类名叫 `File`，会遮蔽 `java.io.File`

```java
public class File {          // ← 类名就叫 File
```

这在当时**没有爆出任何错误**——因为代码里只 import 了 `FileInputStream`、`FileOutputStream`、`IOException`，**从来没 import 过 `java.io.File`**，所以不构成冲突。

但这个雷是真实存在的。真去写 `import java.io.File;`，编译器当场拒绝：

```
错误: 已在该编译单元中定义File
import java.io.File;
       ^
```

**结论**：类名可以继续叫 `File`，但**在这个文件里想用 `java.io.File` 就必须写全限定名**，不能 import。想省事就改名 `FileDemo` / `FileCopy`。

**收获**：默认包下的类名和 `java.io` 里的常用类重名（`File`、`List`、`Date`…）是个隐形坑，早晚会以「为什么我的 import 报错」的形式回来。**同一份作业里还有个 `Name` 类**，同理。

---

### 问题 7（附带）：`static void main` 少了 `public`

```java
static void main(String[] args) {      // 标准写法是 public static void main
```

当前环境（JDK 27）能跑——JDK 25 起 JEP 512 放宽了入口方法的要求，不再强制 `public`。但换到 JDK 21 或更老的机器/评测机，会直接报：

```
错误: 在类 File 中找不到主方法, 请将主方法定义为:
   public static void main(String[] args)
```

这是典型的「在我这儿好好的、到别处就崩」。05 的三道题都是这个写法，一并记在这儿。

## 四、最终代码

```java
import java.io.FileInputStream;
import java.io.FileOutputStream;
import java.io.IOException;

public class File {
    static void main(String[] args) {
        try (FileInputStream fileInputStream = new FileInputStream("doro.jpg");
             FileOutputStream fileOutputStream = new FileOutputStream("doro_copy.jpg")) {
            byte[] bytes = new byte[1024];
            int len;
            while ((len = fileInputStream.read(bytes)) != -1) {
                fileOutputStream.write(bytes, 0, len);
            }
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}
```

## 五、运行与验证

「复制」的判据是**逐字节一致**，不是「生成的文件能打开」：

```
104031 字节  2025-08-25 19:29:28  doro.jpg
104031 字节  2026-10-05 18:16:53  doro_copy.jpg
字节完全一致
```

首尾也对得上：开头都是 `ff d8 ff e0 00 10 4a 46 49 46`（JPEG 的 SOI 标记 + JFIF 头），结尾都是 `... 00 1f ff d9`（EOI 结束标记）。

**关键对照**（写这份记录时重跑，数字与原会话一致）：

| 写法 | 产物大小 | 结论 |
| --- | --- | --- |
| `write(bytes, 0, len)` | 104031 | 与原图逐字节一致 ✅ |
| `write(bytes)` | 104448 | 尾部多 417 字节，图片照样能打开 ❌ |

## 附：几种复制方式的性能对比（顺带实测）

跑通之后追问了「为什么这样就能复制图片」，顺手把几种常见写法放在同一份 64 MB 文件上比了一遍（JDK 27 / Windows 11，各计时一轮）：

| 写法 | 耗时 | 吞吐 |
| --- | --- | --- |
| 字节数组 1024 | 603 ms | 106 MB/s |
| 字节数组 8192 | 108 ms | 592 MB/s |
| 字节数组 65536 | 42 ms | 1523 MB/s |
| Buffered 流 + 单字节 read/write | 1809 ms | 35 MB/s |
| Buffered 流 + 数组 read/write | 114 ms | 561 MB/s |
| `FileChannel.transferTo` | 57 ms | 1122 MB/s |
| `Files.copy` | 20 ms | 3200 MB/s |

几点结论：

- **缓冲区大小是这道题最大的性能旋钮**：1024 → 8192 快了 5 倍多，8192 → 65536 又快一倍多。1024 太小，系统调用次数太多。
- **「用了 Buffered 就快」是错的**：`Buffered 流 + 单字节` 是**最慢**的一档（35 MB/s）。`BufferedInputStream` 每次填 8192 字节的缓冲，但 `read()` 一次只给你一个字节，还是要循环 8 万多次。**包装了缓冲流，也必须配数组读。**
- **`Files.copy` 和 `transferTo` 快**，因为数据在**内核态**直接搬运，不经过 Java 堆。生产代码复制文件直接 `Files.copy` 就行。
- **本题用 1024 的数组完全没问题**——图才 104 KB，一次几十毫秒。这里做对比是为了搞清楚「缓冲区到底在干什么」，不是因为它慢。

## 六、概念小结

| 概念 | 一句话记住 |
| --- | --- |
| 相对路径 | 相对 **JVM 工作目录 `user.dir`**，不是源文件目录；IDEA 默认是项目根。排查第一步 `getAbsolutePath()` |
| `FileOutputStream` 构造器 | **没有无参构造器**，5 个候选全都要一个落点参数——API 在逼你想清楚「写到哪」 |
| 流的生命周期 | 输入/输出流代表一次完整读写会话，**开在 try 的括号里**，别放进循环 |
| `append = false` | 默认每次打开都截断文件；开在循环里 = 反复清空自己 |
| `read` 的返回值 | `len` 是**这一轮实际读到几个字节**，必须一路传给 `write(bytes, 0, len)` |
| 缓冲区复用 | 数组是复用的，最后一轮不足一整块时，尾部全是上一轮的残留数据 |
| 脏数据的隐蔽性 | 文件**前面全对、图片还能打开**，只是尾巴多几百字节；只有 `cmp` 能发现 |
| `available()` | 「估计还能读多少」，不是文件长度；本地文件恰好相等，别当通用答案 |
| 类名遮蔽 | 类名叫 `File` 时，本文件内 `import java.io.File` 会报「已在该编译单元中定义File」，要用全限定名 |
| `static void main` | 缺 `public` 在 JDK 25+ 能跑，JDK ≤ 21 报「找不到主方法」 |
| 缓冲区大小 | 1024 → 8192 → 65536，吞吐 106 → 592 → 1523 MB/s；太小会让系统调用次数爆掉 |
| Buffered 流 | 单独包装**不会**自动变快（配单字节读写反而最慢），要配合数组读写 |
| 内核态搬运 | `Files.copy` / `FileChannel.transferTo` 不经过 Java 堆，复制文件的首选 |
