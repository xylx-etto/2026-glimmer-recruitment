## 二、整体思路的演变

这道题我**推翻了三次做法**，每一次都是因为前一次在某处撞墙：

| 阶段 | 我当时的想法 | 后来发现的问题 |
| --- | --- | --- |
| 1 | `new HttpURLConnection(SERVER_URL) { ... }` | 抽象类不能 `new`，**编译根本过不去** |
| 2 | `String json = "trackingNumber:" + trackingNumber + ",phone:" + phone;` | 手搓 JSON，拼出来的根本不是 JSON |
| 3 | `new QueryResponse("pick_code:" + code, "msg:" + msg)` | 以为字段名要自己写进去——**字段名是 fastjson 从类上读的** |
| 4 | `trackingNumber == "exit"` | `==` 比引用，**恒为 false**，退不出循环 |
| 5 | `sendResponseHeaders(400, -1)` 且以为这就把错误信息发出去了 | `-1` 是"**不带 body**"，精心准备的 JSON 一个字节都没发出去 |
| 6 | `Response` 类只写字段和构造，没写 getter | fastjson 看不见字段，序列化出来是 **`{}`** |
| 7 | 全部改对，编译通过、测试全绿 | ✅ 通了 |

**一句话总结思路转变**：从「**照着方法的字面意思猜**」→「**先搞清楚这一段数据要变成什么形状，再去找工具**」。

**这道题最值得记的一点**：踩的坑分成泾渭分明的两类——

- **一类会红**：编译错误。它拦住你、告诉你第几行，**虽然烦但不可怕**。
- **一类是哑的**：编译过、跑得动、不报错，**结果是错的**。第 2、3、4、5 条全是这一类。

后面那一类才是真正耗时间的。第 4 条那个 `==`，程序安安静静地不退出；第 3 条那个字段名，服务端勤勤恳恳回了一串 `{"key":"pick_code:1234"}` 给我。

## 三、逐个问题记录

### 问题 1：`new HttpURLConnection(...)` —— 编译都过不去

**现象**

```
[ERROR] Client.java:[40,68] 不兼容的类型: java.lang.String无法转换为java.net.URL
[ERROR] Client.java:[40,46] 找不到符号
[ERROR]   符号: 构造器 (java.lang.String)
```

**当时的代码**

```java
HttpURLConnection connection = new HttpURLConnection(SERVER_URL) {
    @Override public void disconnect() { }
    @Override public boolean usingProxy() { return false; }
    @Override public void connect() throws IOException { }
};
```

那一大坨 `@Override` 是我在 IDEA 的红线提示下**顺着补出来的**——它说"必须实现抽象方法"，我就一个一个补上了。

**原因**

`HttpURLConnection` 是**抽象类**，它的构造器是 `protected HttpURLConnection(URL)`：

1. **不能 `new`** —— 抽象类代表"概念"，不是"能造出来的东西"。就像你不能"造一个交通工具"，只能造自行车、汽车。
2. **就算能 new，参数也不是 String 而是 URL** —— 所以报的是两个错：类型不匹配 + 找不到 String 参数的构造器。

补 `@Override` 是**方向错了**：我不是要"继承它"，我是要"**拿到它的一个实例**"。

**解决**

```java
URL url = URI.create(SERVER_URL).toURL();
HttpURLConnection connection = (HttpURLConnection) url.openConnection();
```

两步：先给出地址（URL 对象），再问它要一个"具体的"回来。`openConnection()` 返回的是 `URLConnection`，实际对象是它的子类，所以向下转型。

**收获**：**"我觉得它缺什么"和"它实际要什么"经常会差一层。** 收到编译错误时，先别急着按提示补代码，先问"我这个调用方式本身对不对"。IDE 的"必须实现抽象方法"提示，是在**假设"你就是要继承它"的前提下**给的——可这个前提本身就是错的。

### 问题 2：手拼 JSON —— 拼出来的不是 JSON

**当时的代码**

```java
String json = "trackingNumber:" + trackingNumber + ",phone:" + phone;
// 实际得到：trackingNumber:SF123456789,phone:13005433678
```

**原因**

我把它当"一串有格式的文字"来拼，但 JSON 有硬性语法：**值如果是文字，必须带双引号**；整体要用 `{}` 包起来。

对照：

```
我拼的：  trackingNumber:SF123456789,phone:13005433678
应该是：  {"trackingNumber":"SF123456789","phone":"13005433678"}
```

冒号和逗号我其实写对了，缺的是**最外面的大括号**和**值上的双引号**。

**更根本的问题**：我手上**已经有 `QueryRequest` 类，也已经有 fastjson**，却在自己当翻译。手写 JSON 还有个隐藏风险——万一用户输入里带个 `"` 或 `\`，拼出来的字符串就彻底废了，而用工具根本不会遇到这个问题。

**解决**

```java
String json = JSON.toJSONString(new QueryRequest(trackingNumber, phone));
```

**收获**：**有工具就别手搓。** 而且手搓的格式错误是"哑"的——不报错，服务端收到一堆解析不了的东西，只说一句"格式错误"，你还得回头猜是哪一层拼错了。

### 问题 3：字段名以为要自己写 —— 这道题最大的一个误解

**现象**

服务端"成功"发出去了，客户端也收到了，但值全是错的。我最初写的是：

```java
QueryResponse queryResponse = new QueryResponse("pick_code:" + code, "msg:" + msg);
```

我以为 `"pick_code"` 这四个字母加冒号是**必须手动敲进去**的，因为我要告诉 JSON"这个字段叫什么"。

**原因**

**JSON 的键名，是 fastjson 从你类的字段名上读出来的，不用你写。**

```java
public class QueryResponse {
    private String pick_code;    // ← 字段叫 pick_code
    private String msg;          // ← 字段叫 msg
}
```

`JSON.toJSONString(obj)` 时，fastjson 去看这个类，看到两个字段，于是自己拼出 `{"pick_code": <值>, "msg": <值>}`。

所以我写的那句，等于告诉它：

- `pick_code` 字段的值 = `"pick_code:1234"`
- `msg` 字段的值 = `"msg:success"`

**键名跑到值里面去了。**

**解决**

```java
QueryResponse queryResponse = new QueryResponse(code, "success");
//                                                ↑ 只给值，不要 "pick_code:" 这种前缀
```

**一个记忆口诀**：

> **类负责"键名"，构造方法只负责"值"。**

**收获**：这个误解我**同时在三个地方犯了**（Client TODO 2、Server TODO 4、Server TODO 6），因为它是同一个思维定式：**把"我看到的最终结果"当成"我要写进去的原料"**。看到 JSON 里长着 `pick_code`，就以为代码里也得写 `pick_code`。

改完之后回头看，这三个地方是同一个原因——**只要想通一处，三处一起对**。

### 问题 4：`==` 比字符串 —— 静默失效，循环退不出去

**当时的代码**

```java
if (trackingNumber == "exit") { break; }
```

**现象**

不报错。程序正常运行，输入 `exit` 也没反应，只能按 `Ctrl+C` 强杀。

**原因**

`==` 比的是**两个是不是同一个对象**，不是"内容一样不一样"。

`trackingNumber` 是 `scanner.nextLine().trim()` 现读出来的**新对象**，`"exit"` 是写在代码里的**字面量对象**（存在常量池里）——它俩永远不是同一个。

**所以这个判断恒为 `false`，那个 `break` 一辈子执行不到。**

**解决**

```java
if (trackingNumber.equals("exit")) { break; }
```

**为什么容易写错**：因为 Java 里 `int`、`boolean` 这类**基本类型**用 `==` 比大小是完全正确的，`==` 在其它语言里也常常就是"相等"。**只有对象类型才换成 `equals`**，而 `String` 恰好是最常被拿来比较的对象。

**收获**：**`String` 比较内容只能用 `equals`。** 这条是老生常谈，但它在"哑错误"里排第一名——不报错、不异常、不崩溃，只是静静地什么也不做。

### 问题 5：构造函数名写成了另一个类 —— `方法声明无效; 需要返回类型`

**现象**

```
[ERROR] QueryRequest.java:[12,12] 方法声明无效; 需要返回类型
```

**当时的代码**

```java
public class QueryRequest {
    ...
    public QueryResponse(){     // ← 第 12 行，类名叫 QueryRequest，构造却叫 QueryResponse

    }
}
```

**原因**

**构造函数的名字，必须和类名一模一样。**

我写成了 `QueryResponse`，Java 就不把它当构造函数了，转而去当**方法**看——可方法必须有返回类型（`void` / `int` / …），我也没写，于是报"需要返回类型"。

看着像是从另一个文件复制的时候，把类名一起带过来了。

**解决**

```java
public QueryRequest(){ }
```

**收获**：这个报错信息其实**翻译得很准**——"方法声明无效; 需要返回类型"，它是在说"我把你这一行当成方法了"。**读报错时要顺着它的思路想一遍**，而不是只盯着自己的代码。

### 问题 6：`QueryRequest` 没有无参构造 —— 运行时才炸

**现象**

编译完全通过，服务端一启动就崩：

```
com.alibaba.fastjson2.JSONException: create instance error, class com.test.QueryRequest
```

**原因**

fastjson 把 JSON 翻回对象时，走的是这条路：

1. **先造一个空对象**（调**无参构造**）
2. **再一个一个格子填进去**（调 **setter**）

我当时的 `QueryRequest` 只有 `(String, String)` 这个构造，字段还是 `final` 的——**它第一步就造不出空对象**。

**这是个"编译期一声不吭"的坑。** 编译器只知道"你调了 `parseObject`，参数类型对得上"，至于里面那个类能不能被造出来，它管不着。

**解决**

加上无参构造，字段去掉 `final`，补上 setter：

```java
public QueryRequest() { }
public void setTrackingNumber(String trackingNumber) { this.trackingNumber = trackingNumber; }
public void setPhone(String phone) { this.phone = phone; }
```

**顺带纠正一个我当时可能的误解**：我一开始想"加了 `-parameters` 编译参数是不是就行了"。实测**不行**，这条路由不通，还是老老实实写标准 POJO。

**收获**：**能被 fastjson 翻来翻去的类，得长成"标准样子"**——无参构造 + 私有字段 + 全套 getter/setter。满世界 Java 类都那么啰嗦，不是风格问题，是为了给这类工具留接口。

### 问题 7：`QueryResponse` 没有 getter —— 序列化出来是 `{}`

**现象**

`JSON.toJSONString(queryResponse)` 的输出是：

```
{}
```

取件码和 msg **一个都不在里面**，但**也不报错**。

**原因**

**翻出去（对象 → 纸条）时，fastjson 看的是 getter。**

`QueryResponse` 当时只有字段和构造，**一个 getter 都没有**——在 fastjson 眼里，这个对象"没有任何属性"，于是给你一个空对象。

**和问题 6 对着看，这两件事方向相反：**

| 方向 | fastjson 靠什么 | 类上必须有 |
| --- | --- | --- |
| 对象 → 纸条（序列化） | getter | **getter** |
| 纸条 → 对象（反序列化） | 无参构造 + setter | **无参构造 + setter** |

一个类要两头都能用，就得**两样都齐**。

**解决**

补上 `getPick_code()` / `getMsg()` / `setPick_code()` / `setMsg()`。

**收获**：getter/setter 不再是"IDE 生成的样板废话"。**它们就是 fastjson 的接口。** 缺哪一半，哪个方向就哑掉。

### 问题 8：null 字段被吞掉 —— `{"pick_code":null}` 不见了

**现象**

功能已经通了，但我拿 curl 打服务端的 TODO 6 分支时，实际输出是：

```
{"msg":"请求格式错误"}
```

而题目样例要的是：

```
{"pick_code":null,"msg":"请求格式错误"}
```

`"pick_code":null` **整组消失了**。

**原因**

**fastjson 默认不序列化 null 值**——它觉得"空的东西没必要发"。

**解决**

两种选择：

1. 不管它。因为客户端那边 `getString("pick_code")` 在"**键不存在**"和"**键的值是 null**"两种情况下**拿到的都是 null**，行为完全一样。
2. 严格对齐样例，加开关：

```java
JSON.toJSONString(obj, JSONWriter.Feature.WriteMapNullValue)
```

**收获**：**"序列化器有自己的默认策略"**，它不一定把你写的东西原样搬过去。以后遇到"我明明设了值 / 明明有这个字段，对方却没收到"，先想想是不是被这类开关吃掉了。

### 问题 9：空 body → `parseObject` 返回 null

**现象**

做客户端 TODO 4 之前，我先拿 curl 试了服务端"查不到"那条分支，发现返回的是 **空 body**（`sendResponseHeaders(200, -1)`）。

**如果我当时直接写客户端会怎样**——我实测了一下：

```java
JSON.parseObject("")   // → 返回 null（不抛异常！）
```

然后下一句 `response.getPick_code()` 就是**空指针异常**。

**为什么这个最危险**

它不告诉你"是服务端没发东西"，只告诉你"客户端第几行炸了"。**报错的位置和出错的位置隔着一条网络。**

**解决**

两处一起改：

1. **服务端**：查不到时也带上 body —— `{"pick_code":null,"msg":"未查询到取件码"}`
2. **客户端**：再写解析

**顺序反了就会撞上一个莫名其妙的空指针。**

**收获**：**改这种"两头靠网络连着的代码"，要按数据流的方向改。** 上游先把数据发全，下游再去解析。先写下游，等于在一个还没定型的输入上做假设。

### 问题 10：客户端只写了一半判断 —— 屏幕打出 `null`

**现象**

全链路跑通后，输出是这样：

```
输入 SF123456789 + 13005433678  →  1234       ✅
输入 XX000       + 13000000000  →  null       ❌
输入 ZT789123456 + 18505433664  →  t3456      ✅
```

> ↑ 这里的 `t3456` 多打了一个 `t`，是笔误，后来改回 `3456` 了。**这条输出本身是真实的**（当时确实打印成了 `t3456`），所以保留原样，见「十、遗留」第 7 条。

**当时的代码**

```java
JSONObject jsonObject = JSON.parseObject(s);
System.out.println(jsonObject.getString("pick_code"));    // ← 只有这一句
```

**原因**

题目 TODO 4 的原话是：

> 拿到取件码就打印取件码，**拿不到就打印 msg 的内容**

我**只写了前半句**。取不到的时候就把 `null` 打出来了——服务端明明好好回了一句"未查询到取件码"，被我丢掉了。

**解决**

```java
String code = jsonObject.getString("pick_code");
if (code != null) {
    System.out.println(code);
} else {
    System.out.println(jsonObject.getString("msg"));
}
```

**收获**：**题目里"……就……，否则……"这种句式，是两句，不是一句。** 我当时大概是读到"拿到取件码就打印取件码"就觉得自己懂了，眼睛划过了后半句。

### 问题 11：那个用不上的 `import java.io.OutputStream;`

**现象**

题目给的 `Client.java` 顶部有这么一行：

```java
import java.io.OutputStream;
```

我一开始以为它是为"把 JSON 写进请求体"那句准备的。后来删掉一试，**编译一点问题都没有**。

**原因**

**import 只有在「你在代码里写出这个类型名」的时候才需要。**

我写的是：

```java
connection.getOutputStream().write(json.getBytes(StandardCharsets.UTF_8));
```

从头到尾**没出现过 `OutputStream` 这个词**——`getOutputStream` 是**方法名**，是连在一起的一整块，跟类型名不是一回事。

**题目当初为什么给这个 import？** 因为模板大概预期的写法是**分两步**：

```java
OutputStream out = connection.getOutputStream();   // ← 这里把 OutputStream 写出来了
out.write(json.getBytes(StandardCharsets.UTF_8));
```

这样写，这个名字就出现在代码里了，import 才有用武之地。**我的链式写法更短，所以不需要它。两种都对。**

**顺带发现的两个**：扫了一遍整个包，还有两个没清掉的——

| 文件 | 那个 import | 为什么多余 |
| --- | --- | --- |
| `Server.java` | `java.io.OutputStream` | 同样从没写出这个词 |
| `QueryResponse.java` | `com.alibaba.fastjson2.JSON` | `serialize` 方法删掉之后，这个类就不再用 fastjson 了 |

**留着有影响吗？没有。** 实测 `javac -Xlint:all` **一个字都不报**未使用的 import——编译时它就被丢掉了，对结果零影响。IDEA 会用灰字提示，`Ctrl + Alt + O` 一键清理。

**收获**：**import 是跟着「你写出了哪个类型名」走的，不是跟着「你调用了哪个方法」走的。** 改写法的时候，import 要跟着一起看一眼。

### 问题 12（附带）：`URL(String)` 自 Java 20 起已过时

**现象**

IDEA 提示：

```
java.net.URL 中的 URL(java.lang.String) 已过时
```

开 `-Xlint:deprecation` 编译，能实锤拿到这句：

```
[WARNING] Client.java:[41,25] java.net.URL中的URL(java.lang.String)已过时
```

**先定性：这是警告，不是错误**

| | 意思 | 编译器的态度 |
| --- | --- | --- |
| **错误** | 这代码不对 | 不让你过 |
| **警告** | 这写法将来会被删 | **让你过**，只提醒一句 |

**注意开头是 `[WARNING]`**——项目照常编译成功、8 个测试全绿、jar 正常打出来。

**原因**

从 **Java 20** 起，`java.net.URL` 的**所有公开构造函数**都被标记为过时。官方理由是：处理地址字符串的编解码应该用 `URI`，`URL` 这方面一直不合规（不按 RFC 2396 做编解码）。

**注意**：被弃用的**只有构造函数**，`openConnection()` 好好的。

**解决**

```java
URL url = URI.create(SERVER_URL).toURL();
```

`URI` 负责"读懂这串地址"，`toURL()` 负责"转成 URL 对象"。

**一个好消息**：`toURL()` 抛的 `MalformedURLException` 是 `IOException` 的子类，外层那个 `catch (IOException e)` 直接能兜住，**不用额外加 try/catch**。

改完再跑 `javac -Xlint:all`：**一条警告都没有了。**

**收获**：**分清"错误"和"警告"。** 新手常见反应是控制台一出黄字就慌，以为全完了。实际上编译器的话分三档：

| 档 | 意思 | 这道题里的例子 |
| --- | --- | --- |
| **error** | 不让你过 | `QueryRequest.java:[12,12] 方法声明无效; 需要返回类型` |
| **warning** | 让你过，提醒一句 | `URL(java.lang.String)已过时` |
| **提示** | 建议，IDE 里的灰字 | "未使用的 import" |

**能区分这两者，就知道什么时候该停下来修、什么时候可以继续往前跑。**

### 问题 13（附带）：JDK 27 下那四行 `sun.misc.Unsafe` 警告

**现象**

跑 Client 或者 Server，控制台开头出现这么四行：

```
WARNING: A terminally deprecated method in sun.misc.Unsafe has been called
WARNING: sun.misc.Unsafe::arrayBaseOffset has been called by com.alibaba.fastjson2.util.JDKUtils (file:/C:/Users/%e6%98%9f%e8%af%ad%e8%90%bd%e5%bc%a6/.m2/repository/com/alibaba/fastjson2/fastjson2/2.0.51/fastjson2-2.0.51.jar)
WARNING: Please consider reporting this to the maintainers of class com.alibaba.fastjson2.util.JDKUtils
WARNING: sun.misc.Unsafe::arrayBaseOffset will be removed in a future release
```

第一反应是慌：**"will be removed in a future release"**，我的程序是不是快坏了？

**先定性：又是警告，不是错误**

四行全部以 `WARNING:` 开头，**零堆栈**——没有任何一行 `at 包名.类名.方法(文件名.java:行号)`。

同一时刻程序照常跑完：

```
请输入快递单号（输入exit退出）: 请输入手机号: 1234
```

**谁在喊：不是我的代码在喊**

关键在第二行那句话：

```
sun.misc.Unsafe::arrayBaseOffset has been called by com.alibaba.fastjson2.util.JDKUtils
                                              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 元凶在这
```

**是 fastjson2 在喊，不是我在喊。** 它内部有个 `JDKUtils` 类，用 JDK 的内部 API `sun.misc.Unsafe` 来加速（拿数组元素的内存偏移量，比走反射快）。

`sun.misc.Unsafe` 这个 API 从来没被官方承诺过，名字里的 `sun.misc` 就是"Sun 公司内部杂项"的意思——**它从来不是给外人用的**。

**那串像乱码的路径**

```
file:/C:/Users/%e6%98%9f%e8%af%ad%e8%90%bd%e5%bc%a6/.m2/repository/...
                 ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                 这是「星语落弦」四个字的 URL 编码，不是乱码
```

`%e6%98%9f` = 星，`%e8%af%ad` = 语，`%e8%90%bd` = 落，`%e5%bc%a6` = 弦（UTF-8，每字 3 字节）。这是 Maven 本地仓库路径，**只是用户名里有中文所以被编码了，跟报错没关系**。

**为什么现在才出现**

| 时间点 | 发生了什么 |
| --- | --- |
| JDK 23 | `Unsafe` 的内存访问方法被标记为 **terminally deprecated**（"最终弃用"，意思是准备删了） |
| JDK 24 | 只要有人调用，JVM 就在**首次调用时**打印一次警告 |
| 我这台机器 | JDK **27** 跑 fastjson2 **2.0.51**，两个一撞就出声 |

因为是"每个 JVM 生命周期、每个方法只打一次"，所以现象是：**每次 Run 都能看到这 4 行，但一次运行里不会刷屏。**（我一开始以为是我某个循环里出了大问题，一看只有一次，就排除了这个可能。）

**解决**

| 做法 | 效果 |
| --- | --- |
| **无视**（推荐） | 这是**第三方库的技术债，不是我的**。等 fastjson2 自己改 |
| 加 JVM 参数 `--sun-misc-unsafe-memory-access=allow` | 实测这 4 行直接消失（该参数的默认值是 `warn`） |
| 升 fastjson2 版本 | 得看新版是否已弃用 `Unsafe`，不保证 |

IDEA 里加参数的位置：`Run → Edit Configurations → VM options`。

**收获一：判别"红字 / 黄字"有个更可靠的办法——看有没有堆栈**

问题 12 里我总结过"error 不让你过，warning 让你过"。但这次发现，光靠"红色还是黄色"不够稳，因为**有些终端把警告也渲染成红色**。更可靠的是看结构：

| | 长什么样 |
| --- | --- |
| **真报错** | 有 `Exception` / `Error`，**并且**带 `at 包名.类名.方法(文件名.java:行号)` 的堆栈 |
| **警告** | 以 `WARNING:` 或 `[WARNING]` 开头，**没有堆栈** |

**"有没有堆栈"比"什么颜色"可靠得多。**

**收获二：一条警告，先看"谁发的"，再看"说了什么"**

这条警告里的

```
has been called by com.alibaba.fastjson2.util.JDKUtils
```

**`by` 后面那个类名，一眼就说明不是我的代码在出问题。**

"JDK 版本比库新"这类警告是家常便饭——**库追 JDK，永远慢半拍**。以后见到 `terminally deprecated` 这种词，第一件事是找 `by` 后面那个类名，看是不是自己写的。

### 问题 14：`Connection refused: connect` —— 我把它错怪成了"输入不对"

**现象**

Server 没起的时候，**不管输入什么**，都打印同一句：

```
请求发生错误: Connection refused: connect
```

我当时的理解是：**"输入格式不对，所以连接被拒绝了。"**

这个理解是错的，而且错得很自然——因为我是先试了一条正确的（那次 Server 还活着，成功了），紧接着试了条乱的，就撞上这句，于是**把"输入乱"和"连接被拒"联系在了一起**。

**定性：它跟输入一点关系都没有**

做了个对照实验，**故意不起 Server**，同样的客户端跑两次：

| 输入 | 输出 |
| --- | --- |
| `SF123456789` + `13005433678`（完全正确） | `请求发生错误: Connection refused: connect` |
| `AAA` + `111`（乱填） | `请求发生错误: Connection refused: connect` |

**一模一样，一个字都不差。**

所以它跟输入无关，是**每次都在报**——只是正确的那次我恰好在 Server 还活着的时候跑的，制造了一个假的因果。

**原因：它发生在"还没开始说话"的阶段**

`Connection refused` 是 `java.net.ConnectException`，它的来源是**操作系统**，不是服务端——因为**服务端根本没有参与这件事**：

```
客户端 connect() ──SYN──▶ 127.0.0.1:8000
                           （这个端口上没人在听）
         ◀──RST───
   ConnectException: Connection refused: connect
```

操作系统一看这个端口没有进程在监听，直接回一个 RST，JVM 把它翻译成 `Connection refused`。

**它抛在哪一行**

```
Client.java:46
    connection.getOutputStream().write(json.getBytes(StandardCharsets.UTF_8));
//             ^^^^^^^^^^^^^^^^^^ setDoOutput(true) 之后，这一句才真正去连网
```

**关键推论**：因为抛在这里，`json` 那个字节数组**根本没写出去**。

```
请求压根没上路 → Server.java 里那些 msg 代码，一行都没执行过
```

**"连接失败"有四种，报错关键字直接告诉你卡在哪一层**

| 报错 | 发生在哪 | 意思 |
| --- | --- | --- |
| `Connection refused: connect` | TCP 握手（`connect()`） | 端口上没人听 → **Server 没起** |
| `Connection timed out` | TCP 握手 | 地址不通 / 被防火墙拦了 |
| `Connection reset` | 已经连上之后 | 服务端中途把连接掐了 |
| `Server returned HTTP response code: 400` | 响应已经回来了 | 见问题 15 |

**排查手法：先确认 Server 到底在不在**

```
$ netstat -ano | findstr :8000
（没有 LISTENING 行 = Server 没在跑）
```

或者更直接——看 IDEA 里 Server 那个运行窗口有没有这行：

```
Server started on port 8000
```

**收获：报错先问"它在哪一层"，别急着改代码。**

网络程序有两拨人隔着一条线干活，从敲回车到看见结果，中间有这么多个环节：

```
输入校验 → 拼 JSON → TCP 连接 → 发请求体 → 服务端处理 → 收响应 → 解析响应
                       ↑                                        ↑
                问题 14 卡在这                          问题 15 卡在这（还有问题 16）
```

**报错信息里的关键字，直接暴露了它在哪一层**——`connect` 说明连都没连上，**跟业务逻辑一点关系都没有**。这时候去改输入校验、改 msg 内容，全是白费力气。

（这也是为什么我一开始那么自然地错怪了输入：**句子里有个 `refused`，听起来像"被拒绝了"，像是有个服务端在审我的请求。其实那时候连服务端都没有。**）

### 问题 15：400 的 msg 到不了屏幕 —— 响应体在**另一条流**上

**现象**

问题 14 解决（Server 起上了）之后，新的问题出现了：**有一半的 msg 还是看不见。**

服务端明明返回了，客户端却只打状态码。实测：

```
=== 单号留空 ===
请输入快递单号（输入exit退出）: 请输入手机号: 查询失败，状态码: 400
```

但服务端**确实把 msg 发出去了**——绕过客户端，用 curl 直接看原始响应，实锤：

```
$ curl -X POST -H "Content-Type: application/json" \
       -d '{"trackingNumber":"","phone":"13005433678"}' \
       http://localhost:8000/query
{"msg":"单号或手机号为空"} <- HTTP 400
```

**服务端没毛病，问题在客户端取不到。**

**原因：`HttpURLConnection` 按状态码把响应体分到了两条流上**

这是个设计成这样的行为，不是 bug：

| 状态码 | 响应体在哪 | 用 `getInputStream()` 会怎样 |
| --- | --- | --- |
| **2xx** | `getInputStream()` | 正常读到 |
| **4xx / 5xx** | **`getErrorStream()`** | **直接抛 `IOException`** |

它这么分是有道理的：`getInputStream()` 的语义是"拿我预期的结果"，而 4xx/5xx 是"**没拿到结果，拿到了一份错误说明**"。错误说明被归到了 `getErrorStream()`。

**⚠️ 中间走过的弯路（这一段是真实记录，别跳过）**

我第一次改的时候，判断的是："问题出在读取 body 的那三行被包在 `if` 里了"——于是把它们**提到 `if` 外面**，让两条路共用：

```java
InputStream inputStream = connection.getInputStream();   // 从 if 里提到外面
String s = Client.readBody(inputStream);
JSONObject jsonObject = JSON.parseObject(s);
if (connection.getResponseCode() == 200) { ... } else { ... }
```

**这个改法方向就是反的。** 跑出来是这个：

```
=== 单号留空 ===
请求发生错误: Server returned HTTP response code: 400 for URL: http://localhost:8000/query
```

**看清楚发生了什么：** `getInputStream()` 一见 400 就直接抛 `IOException`，程序**当场跳到最外层的 `catch`**（`Client.java:73`），

```java
} catch (IOException e) {
    System.out.println("请求发生错误: " + e.getMessage());
}
```

**`else` 分支里那两行，压根没被执行过。**

**这暴露了一件我原来完全没意识到的事：**

> **我 `else` 分支里的代码是"写在那里"的，但它从来没有被执行过。**
>
> 它是一段**死代码**——而且是最阴的那种死代码：**不报错、不警告、编译器完全不管**。它只是安静地待在那里，让我以为"400 的情况我处理过了"。

**正确改法：先判状态码，再决定拿哪条流**

```java
if (connection.getResponseCode() == 200) {
    // 2xx —— 正常结果
    InputStream inputStream = connection.getInputStream();
    String s = Client.readBody(inputStream);
    JSONObject jsonObject = JSON.parseObject(s);
    String code = jsonObject.getString("pick_code");
    if (code != null) {
        System.out.println(code);
    } else {
        System.out.println(jsonObject.getString("msg"));
    }
} else {
    // 4xx —— 服务端说人话的那条通道在 getErrorStream()
    InputStream inputStream = connection.getErrorStream();
    String s = Client.readBody(inputStream);
    JSONObject jsonObject = JSON.parseObject(s);
    System.out.println("查询失败，状态码: " + connection.getResponseCode());
    System.out.println(jsonObject.getString("msg"));
}
```

**顺序是关键**：`getResponseCode()` 必须先调，它是"决定走哪条路"的开关。而"先取流、后判码"是反的——**流一取错，后面全错**。

`readBody()` 不用改一行，两条流它都吃（它只认 `InputStream` 这个类型，不关心来路）。

改完实测：

```
=== 单号留空 ===
请输入快递单号（输入exit退出）: 请输入手机号: 查询失败，状态码: 400
单号或手机号为空
```

**收获一：这一行决定了"服务端写的 msg 到底有没有用"**

这道题里服务端精心写了三种 msg：

```java
"单号或手机号为空"    // 400
"请求格式错误"        // 400
"未查询到取件码"      // 200
```

**三条里两条写在 400 上。**

不改客户端这几行的话，服务端写多少 msg 都等于白写——这一整道题里跟 msg 相关的所有代码，**最后全卡在这一行上**。反过来说：**写 msg 的时候就得想到"对面收不收得到"**，不然就是自己跟自己写信。

**收获二：`getErrorStream()` 可能返回 `null`**

如果服务端返回 4xx 但**不带响应体**，`getErrorStream()` 会返回 `null`。这时候 `readBody(null)` 里的 `new InputStreamReader(null)` 抛的是 **`NullPointerException`**——

**不是 `IOException`，外层的 `catch (IOException e)` 接不住，客户端会直接崩掉。**

我这道题碰不到，因为服务端的 400 一定带 body。但 `Server.java` 里**就算有一个分支是不带 body 的**：

```java
if (!"POST".equals(exchange.getRequestMethod())) {
    exchange.sendResponseHeaders(405, -1);   // 第二参 -1 = 不带 body
    ...
}
```

**现在客户端只发 POST，撞不到；哪天我改成发 GET 玩，就会撞上。** 先记在这。

### 问题 16：`请求格式错误` 这条分支，我的测试工具**够不着**

**现象**

问题 15 改完之后，另外两条 msg 都能显示了，`请求格式错误` 还是从来没出现过。

**先说结论：这次服务端没问题，是我的测试工具构造不出触发条件。**

**这条分支的触发条件**

`请求格式错误` 来自 `Server.java` 的 `catch (Exception e)`，只有**请求体本身是坏的**才会进。用 curl 手工构造，三种都能触发：

```
$ curl -d '' ...                                  → {"msg":"请求格式错误"}  HTTP 400   ← 空 body
$ curl -d '{trackingNumber: oops' ...             → {"msg":"请求格式错误"}  HTTP 400   ← 坏 JSON
$ curl -d '{"trackingNumber":"SF123456789"}' ...  → {"msg":"请求格式错误"}  HTTP 400   ← 缺字段
```

第三条的链路值得单独说：**缺字段 → `request.getTrackingNumber()` 返回 `null` → `null.isBlank()` 抛 NPE → 被 `catch (Exception e)` 收走 → 变成"请求格式错误"。**

**为什么我的客户端触发不了**

看客户端发请求体那行：

```java
String json = JSON.toJSONString(new QueryRequest(trackingNumber, phone));
```

**`JSON.toJSONString()` 不可能生成坏 JSON。** 这是它的本职工作。

哪怕我什么都不输入，发出去的也是：

```json
{"trackingNumber":"","phone":"13005433678"}
```

——合法 JSON、字段齐全、两个字段都在。

所以 `catch` 那条路，**用我自己的客户端一次都进不去**。

**这暴露的问题，比 bug 本身更值得记**

原来的思考路径是这样的：

```
改完代码 → 跑一下 → 看不见 msg → "还是有问题，接着改"
                ↑
        我把"看不见"直接等于"代码写错了"
```

**但"看不见"有两种完全不同的原因：**

| 原因 | 该做什么 |
| --- | --- |
| 代码写错了 | 改代码 |
| **我的测试工具构造不出触发条件** | **换工具（curl / Postman），代码一个字都不用动** |

**我默认了是第一种，于是对着客户端改了半天，方向从一开始就是偏的。**

**验证一条分支之前，先问一句：**

> ### **"我手头这个工具，能不能构造出触发它的输入？"**

客户端的输入来自 `Scanner`，**它只能给出两个字符串**——这就是它的表达能力的上限。而 `请求格式错误` 需要的是"一个非 JSON 的请求体"，**这个输入根本不在 `Scanner` 的值域里**。

这类分支，必须用"能直接发原始 HTTP 报文"的工具来验：

```bash
curl -X POST http://localhost:8000/query \
  -H "Content-Type: application/json" \
  -d '{"trackingNumber":"SF123456789"}'
```

**收获：把"测不到"和"没写好"分开**

这两种情况的**现场长得一模一样**——都是"跑了一遍，没看到预期输出"。但**处理方向完全相反**：

- 一种是**回到代码**找问题
- 一种是**回到测试工具**找问题，代码别动

**判断方法**：先反问自己"**这个输入，我的手能打出来吗？**"

- 能打出来 → 程序没反应 → 是代码问题
- **压根打不出来 → 那是测试工具的问题，不是代码的问题**

这也补上了我原来那条"只跑一条路径不算验证"的另一半：

> 原来：**跑一条不算验证**（异常分支才是 bug 的藏身处）
>
> 现在补上：**先确认你那条路径跑得到**——**够不着的分支，你"验"了也是自己骗自己。**

### 4.3 四种"失败"分别在哪一步被拦住

| 你看到的 | 断在第几步 | 谁拦的 |
| --- | --- | --- |
| `请求发生错误: Connection refused: connect` | ④（连都连不上，`getOutputStream()` 就抛了） | **操作系统**：8000 端口上没人听 |
| `请求发生错误: Server returned HTTP response code: 400` | ⑮（拿错了管子） | 客户端自己：用 `getInputStream()` 去读 400 的 body |
| `查询失败，状态码: 400` + `单号或手机号为空` | ⑰（走 else 分支） | 服务端盖了 400 的章 |
| `未查询到取件码` | ⑰（走 else 分支） | 数据里没这条，服务端如实告知 |

**前两行的区别特别值得看**：它们**都是"请求发生错误"开头**，给人的感觉是同一类问题，其实**一个发生在 TCP 层（④）、一个发生在读响应体的时候（⑮）**，中间隔了整整十步。

> **这也是我这轮最大的一个教训：不能靠"报错信息长得像"来分类问题。**
> 问题 14 和问题 15 的第二行，字面上看都是"请求出错"，但一个要去开 Server，一个要去改客户端那一行——**方向完全相反。**

**再看后两行的区别**：都是"没查到"，但一个是**协议层**说"你这请求有问题"（400），一个是**业务层**说"请求没问题，就是没这条数据"（200 + 说明文字）。**这两个不是一回事。**

### 4.4 一个我原来没想通的事：为什么 Server 里"收信"和"回信"是同一个对象

`HttpExchange` 身上既有 `getRequestMethod()` / `getRequestBody()`，又有 `sendResponseHeaders()` / `getResponseBody()`。

因为它代表的是**"一次往返"这件事本身**，不是"一封信"。收到的那封和要回的那封，都归它管。

## 五、HTTP 常用方法与逻辑速查

这一节也是给自己以后回看的。**我做这题时最大的困难不是"想不通逻辑"，是"根本不知道有哪些方法可以调"。**

### 5.1 先建立画面

- **请求（Request）** = Client 寄给 Server 的信
- **响应（Response）** = Server 回给 Client 的信

一封信有四部分：

| | 请求里的意思 | 这道题里的值 |
| --- | --- | --- |
| **方法** | 我想干什么 | `POST` |
| **路径** | 我去哪个窗口办 | `/query` |
| **头（Header）** | 附带的说明 | `Content-Type: application/json` |
| **体（Body）** | 信件内容本身 | `{"trackingNumber":...}` |

响应少了"方法/路径"，多了"状态码"。

### 5.2 客户端（`java.net`）常用方法

| 类 | 方法 | 干什么 |
| --- | --- | --- |
| `URI` | `URI.create("http://...")` | 把地址字符串**解析**成 URI |
| `URI` | `.toURL()` | URI → URL |
| `URL` | `url.openConnection()` | 要一条线路（返回 `URLConnection`，要转型） |
| `HttpURLConnection` | `setRequestMethod("POST")` | 信封上写"我要 POST" |
| `HttpURLConnection` | `setDoOutput(true)` | 声明"我要往信封里塞东西" |
| `HttpURLConnection` | `setRequestProperty("Content-Type", "...")` | 信封上写"我塞的是 JSON" |
| `HttpURLConnection` | `getOutputStream()` | 拿到**写**请求体的管子 |
| `HttpURLConnection` | `getResponseCode()` | 看对方盖的章（200 / 400 / 405） |
| `HttpURLConnection` | `getInputStream()` | 拿到**读**响应体的管子（**只有 2xx 能读**） |
| `HttpURLConnection` | `getErrorStream()` | 拿到**读错误说明**的管子（**4xx / 5xx 的 body 在这条上**） |
| `HttpURLConnection` | `disconnect()` | 挂断 |

### 5.3 服务端（`com.sun.net.httpserver`）常用方法

`HttpExchange` = "一次往返"这个对象，**收信和回信都在它身上**。

**读对方寄来的：**

| 方法 | 干什么 |
| --- | --- |
| `getRequestMethod()` | 他用的什么方法 |
| `getRequestBody()` | 拿到请求体的管子 |
| `getRequestBody().readAllBytes()` | 一次性全读出来（**字节**） |

**回信：**

| 方法 | 干什么 |
| --- | --- |
| `getResponseHeaders().set(...)` | 设响应头（**必须在盖章之前**） |
| `sendResponseHeaders(状态码, 字节数)` | **盖章** + 说明 body 有多长 |
| `getResponseBody()` | 拿到写响应体的管子 |
| `getResponseBody().write(字节数组)` | 把 body 写进去 |
| `close()` | 收工 |

### 5.4 四个必须记住的规则

**规则一：顺序不能乱**

```
① URI/URL          ← 有地址
② openConnection   ← 有线路
③ 所有 setXxx      ← 先把信封写好
④ getOutputStream + write   ← 才能塞纸条
⑤ getResponseCode  ← 才能看章
⑥ getInputStream   ← 才能拆回信
```

**③ 里的所有 `setXxx` 必须在 ④ 之前。** ④ 一旦开始写，信封就"封口"了，再改就不作数（会抛异常）。

服务端同理：

```
设响应头 → sendResponseHeaders → write body → close
```

**规则二：管子只认字节，不认字符串**

```java
字符串.getBytes(StandardCharsets.UTF_8)          // 字符串 → 字节
new String(字节数组, StandardCharsets.UTF_8)      // 字节 → 字符串
```

**规则三：`sendResponseHeaders` 第二个参数是"字节数"，不是"要不要发"**

| 填什么 | 什么意思 |
| --- | --- |
| `-1` | 我**不带** body，光盖个章 |
| `0` | 我要带，但长度不确定（分块传输） |
| `正数 N` | 我要带 N 字节 |

**这里有个坑**：`json.length()` 数的是**字符个数**，不是字节数。中文一个字在 UTF-8 里占 **3 个字节**：

```
"手机号不正确"  →  length() = 6 ，getBytes(UTF_8).length = 18
```

长度报少了，对方收到的就是半个字。**口诀：盖的章说多少字节，就得用 `getBytes(...).length` 来算。**

**规则四：读响应体，得先看状态码——两条流，二选一**

这是这一轮才补上的一条（问题 15），**前面五节里全都没写到，所以单独拎出来当规则。**

| 状态码 | 响应体在哪条管子上 | 拿错会怎样 |
| --- | --- | --- |
| **2xx** | `getInputStream()` | — |
| **4xx / 5xx** | **`getErrorStream()`** | `getInputStream()` **直接抛 `IOException`**，程序跳过后面所有代码 |

```java
int status = connection.getResponseCode();          // ① 先看章
InputStream is = (status == 200)
        ? connection.getInputStream()               // ② 再按章的号码选管子
        : connection.getErrorStream();
String body = 读(is);                                // ③ 两条管子读法完全一样
```

**为什么这么设计**：`getInputStream()` 的语义是"拿我预期的结果"，而 4xx/5xx 是"**没拿到结果，拿到了一份错误说明**"。错误说明被归到了另一条管子。

**口诀：先看章，再选管子。** 顺序反了必错——因为**管子一旦选错，后面写得再对也没用**。

**附带一个坑**：服务端 4xx **不带 body** 时，`getErrorStream()` 返回 **`null`**。这时去读会抛 **`NullPointerException`**（不是 `IOException`，普通的 `catch (IOException)` 接不住）。本项目里 405 分支就是不带 body 的。

### 5.5 常用状态码

| 码 | 名字 | 什么时候用 |
| --- | --- | --- |
| `200` | OK | 办成了 |
| `400` | Bad Request | 你送来的东西不对/看不懂 |
| `404` | Not Found | 没这个路径 |
| `405` | Method Not Allowed | 该 POST 你用了 GET |
| `500` | Internal Server Error | 我这边自己出错了 |

### 5.6 怎么找到"还有哪些方法"

**别背。用这两个键：**

- 打出 `connection.` 停一下 → IDEA 弹出这个对象的**所有方法**
- 光标放在 `HttpURLConnection` 上按 `Ctrl + B` → 跳到它的定义，从上往下扫
- 选中方法按 `Ctrl + Q` → 弹一句话说明

**另外，题目给的 `import` 列表本身就是工具箱清单。** 这道题给我的 import 里有 `InputStream` / `OutputStream` / `InputStreamReader` / `BufferedReader` / `StandardCharsets` / `JSON`——它没给 `File`、没给 `Socket`，那就说明这题用不到那些。

### 6.2 起点 vs 终点：逐处对照

| | 起点 | 终点 | 对应的问题 |
| --- | --- | --- | --- |
| **Client 建连接** | `new HttpURLConnection(SERVER_URL) { ... }` 匿名继承，**编译不过** | `URI.create(...).toURL()` + `url.openConnection()` 转型 | 问题 1、12 |
| **Client 判断退出** | `trackingNumber == "exit"` | `trackingNumber.equals("exit")` | 问题 4 |
| **请求体怎么来** | `"trackingNumber:" + trackingNumber + ",phone:" + phone` 手拼 | `JSON.toJSONString(new QueryRequest(...))` | 问题 2 |
| **请求体有没有发出去** | 信封写好了，**里面是空的**（没有 `write`） | `connection.getOutputStream().write(...)` | — |
| **响应怎么处理** | TODO 4 是空的，**一行没写** | `readBody` → `parseObject` → 判断 `pick_code` 是否为 null | 问题 10 |
| **两个 POJO** | 字段 `final` + 只有带参构造 + **QueryResponse 一个 getter 都没有** | 无参构造 + getter + setter 全套 | 问题 6、7 |

| **400 的响应体怎么读** | `else` 分支里压根没读（或误用 `getInputStream()`，**一取就抛异常**） | **先判状态码**，4xx 走 `getErrorStream()` | 问题 15 |

**一句话看这个转变**：起点那份，**每一处都在"照着自己想象的形状"写**——想象 HTTP 连接可以 new、想象 JSON 要手拼、想象字段名要自己写、想象 `-1` 是"随便填"。终点那份，每一处都**对齐了"它实际要什么"**。

```java
package com.test;

import com.alibaba.fastjson2.JSON;
import com.alibaba.fastjson2.JSONObject;

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStream;
import java.io.InputStreamReader;
import java.net.HttpURLConnection;
import java.net.URI;
import java.net.URL;
import java.nio.charset.StandardCharsets;
import java.util.Scanner;

public class Client {
    private static final String SERVER_URL = "http://localhost:8000/query";

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);
        while (true) {
            try {
                // 读取用户输入的快递单号
                System.out.print("请输入快递单号（输入exit退出）: ");
                String trackingNumber = scanner.nextLine().trim();
                if (trackingNumber.equals("exit")) {
                    break;
                }

                // 读取用户输入的手机号
                System.out.print("请输入手机号: ");
                String phone = scanner.nextLine().trim();

                // 用 fastjson 构造请求体
                String json = JSON.toJSONString(new QueryRequest(trackingNumber, phone));

                // 创建连接，写入请求体，发送 POST
                URL url = URI.create(SERVER_URL).toURL();
                HttpURLConnection connection = (HttpURLConnection) url.openConnection();
                connection.setRequestMethod("POST");
                connection.setDoOutput(true);
                connection.setRequestProperty("Content-Type", "application/json;charset=UTF-8");
                connection.getOutputStream().write(json.getBytes(StandardCharsets.UTF_8));

                // 状态码是 200 才算响应成功
                if (connection.getResponseCode() == 200) {
                    InputStream inputStream = connection.getInputStream();
                    String s = Client.readBody(inputStream);
                    JSONObject jsonObject = JSON.parseObject(s);
                    String code = jsonObject.getString("pick_code");
                    if (code != null) {
                        System.out.println(code);
                    } else {
                        System.out.println(jsonObject.getString("msg"));
                    }
                } else {
                    // 4xx/5xx 的响应体在 getErrorStream() 上，不是 getInputStream()
                    InputStream inputStream = connection.getErrorStream();
                    String s = Client.readBody(inputStream);
                    JSONObject jsonObject = JSON.parseObject(s);
                    System.out.println("查询失败，状态码: " + connection.getResponseCode());
                    System.out.println(jsonObject.getString("msg"));
                }
                connection.disconnect();
            } catch (IOException e) {
                System.out.println("请求发生错误: " + e.getMessage());
            }
        }
        scanner.close();
        System.out.println("客户端已退出");
    }

    /** 读取响应体：把InputStream按UTF-8读成一个字符串 */
    private static String readBody(InputStream is) throws IOException {
        StringBuilder sb = new StringBuilder();
        try (BufferedReader reader = new BufferedReader(new InputStreamReader(is, StandardCharsets.UTF_8))) {
            String line;
            while ((line = reader.readLine()) != null) {
                sb.append(line);
            }
        }
        return sb.toString();
    }
}
```

#### `Server.java`

```java
package com.test;

import com.alibaba.fastjson2.JSON;
import com.alibaba.fastjson2.JSONObject;
import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpHandler;
import com.sun.net.httpserver.HttpServer;

import java.io.IOException;
import java.io.OutputStream;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;
import java.util.HashMap;
import java.util.Map;

public class Server {
    private static final int PORT = 8000;
    // 模拟快递柜数据：key = 快递单号_手机号，value = 取件码
    private static final Map<String, String> expressMap = new HashMap<>();

    public static void main(String[] args) throws IOException {
        initializeExpressData();
        HttpServer server = HttpServer.create(new InetSocketAddress(PORT), 0);
        server.createContext("/query", new QueryHandler());
        server.start();
        System.out.println("Server started on port " + PORT);
    }

    private static void initializeExpressData() {
        // 键的构成是  快递单号_手机号
        expressMap.put("SF123456789_13005433678", "1234");
        expressMap.put("JD987654321_19805433168", "5678");
        expressMap.put("YT456789123_13905479698", "9012");
        expressMap.put("ZT789123456_18505433664", "3456");
    }

    static class QueryHandler implements HttpHandler {
        @Override
        public void handle(HttpExchange exchange) throws IOException {
            // 非POST请求返回405 Method Not Allowed
            if (!"POST".equals(exchange.getRequestMethod())) {
                exchange.sendResponseHeaders(405, -1);
                exchange.close();
                return;
            }

            try {
                // 读取请求体（字节流按UTF-8转成字符串）
                String body = new String(exchange.getRequestBody().readAllBytes(), StandardCharsets.UTF_8);
                // 解析JSON请求，取出单号和手机号
                QueryRequest request = JSON.parseObject(body, QueryRequest.class);
                String trackingNumber = request.getTrackingNumber();
                String phone = request.getPhone();

                // 校验：单号和手机号不能为空
                if (trackingNumber.isBlank() || phone.isBlank()) {
                    JSONObject body1 = new JSONObject();
                    body1.put("pick_code", null);
                    body1.put("msg", "单号或手机号为空");
                    String json = JSON.toJSONString(body1);
                    exchange.getResponseHeaders().set("Content-Type", "application/json;charset=UTF-8");
                    exchange.sendResponseHeaders(400, json.getBytes(StandardCharsets.UTF_8).length);
                    exchange.getResponseBody().write(json.getBytes(StandardCharsets.UTF_8));
                    exchange.close();
                    return;
                }

                // 拼 key，查取件码
                String key = trackingNumber + "_" + phone;
                if (!expressMap.containsKey(key)) {
                    JSONObject body1 = new JSONObject();
                    body1.put("pick_code", null);
                    body1.put("msg", "未查询到取件码");
                    String json = JSON.toJSONString(body1);
                    exchange.getResponseHeaders().set("Content-Type", "application/json;charset=UTF-8");
                    exchange.sendResponseHeaders(200, json.getBytes(StandardCharsets.UTF_8).length);
                    exchange.getResponseBody().write(json.getBytes(StandardCharsets.UTF_8));
                    exchange.close();
                    return;
                }
                String code = expressMap.get(key);

                // 构造响应并发送
                QueryResponse queryResponse = new QueryResponse(code, "success");
                String json = JSON.toJSONString(queryResponse);
                exchange.getResponseHeaders().set("Content-Type", "application/json;charset=UTF-8");
                exchange.sendResponseHeaders(200, json.getBytes(StandardCharsets.UTF_8).length);
                exchange.getResponseBody().write(json.getBytes(StandardCharsets.UTF_8));
                exchange.close();

            } catch (Exception e) {
                QueryResponse queryResponse = new QueryResponse(null, "请求格式错误");
                byte[] bytes = JSON.toJSONBytes(queryResponse);
                exchange.sendResponseHeaders(400, bytes.length);
                exchange.getResponseBody().write(bytes);
                exchange.close();
            }
        }
    }
}
```

> **两处还能再收一下（都还没改，只是想法）**：
> 1. 上面四段"设头 → 盖章 → 写 body → close"几乎一模一样，可以抽成一个 `sendJson(exchange, 状态码, msg)` 方法——**这是重复代码最典型的信号：同一段东西出现三次以上就该抽象了**
> 2. `catch` 分支漏了 `Content-Type`（只有成功路径设了）。现在没出乱码是因为客户端自己指定了 UTF-8，属于"下游兜住了上游的漏"

### 7.3 用 curl 单独验服务端

绕过客户端，直接打服务端，确认它自己的行为：

```
$ curl -s -X POST -H "Content-Type: application/json" \
       -d '{"trackingNumber":"SF123456789","phone":"13005433678"}' \
       http://localhost:8000/query
{"msg":"success","pick_code":"1234"}

$ curl -s -X POST -H "Content-Type: application/json" http://localhost:8000/query
{"msg":"请求格式错误"}          ← 空 body，走了 catch 分支
```

**这两条的价值在于"隔离"**——出问题时能立刻分清是客户端的问题还是服务端的问题，不用在两个进程之间来回猜。

**问题 15 排查时，这一手又用了一次。** 当时客户端只打状态码、看不到 msg，问题就是"到底是服务端没发，还是客户端没收到"。用 curl 打同一组参数，加上 `-w` 把状态码也带出来：

```
$ curl -s -w " <- HTTP %{http_code}\n" -X POST \
       -H "Content-Type: application/json" \
       -d '{"trackingNumber":"","phone":"13005433678"}' \
       http://localhost:8000/query
{"msg":"单号或手机号为空"} <- HTTP 400

$ curl -s -w " <- HTTP %{http_code}\n" -X POST \
       -H "Content-Type: application/json" \
       -d '{"trackingNumber":"SF123456789","phone":""}' \
       http://localhost:8000/query
{"msg":"单号或手机号为空"} <- HTTP 400
```

**看到这两行，责任立刻分清了：服务端发了、发对了、状态码也对 → 问题 100% 在客户端。** 假如这两行是空的，那就是服务端的事，去向完全相反。

**问题 16 里，curl 又派了第三次用场**——`请求格式错误` 客户端构造不出来，只有 curl 能发：

```
$ curl -s -w " <- HTTP %{http_code}\n" -X POST \
       -H "Content-Type: application/json" -d '' \
       http://localhost:8000/query
{"msg":"请求格式错误"} <- HTTP 400

$ curl -s -w " <- HTTP %{http_code}\n" -X POST \
       -H "Content-Type: application/json" -d '{trackingNumber: oops' \
       http://localhost:8000/query
{"msg":"请求格式错误"} <- HTTP 400

$ curl -s -w " <- HTTP %{http_code}\n" -X POST \
       -H "Content-Type: application/json" -d '{"trackingNumber":"SF123456789"}' \
       http://localhost:8000/query
{"msg":"请求格式错误"} <- HTTP 400
```

**一道题里 curl 救了三次。** 结论很明确：**手里得同时握着"客户端"和"curl"两把尺子**——客户端验"整条链路通不通"，curl 验"服务端单方面对不对"。只有一把尺子的时候，出错就分不清是谁的责任。

### 7.4 反向验证：Server 不起的时候

正向跑通了，还得**反向确认一次失败路径**——不然你不知道"成功"是真成功，还是"不管怎样都打印这个"。

关掉 Server，同样的客户端**用两种输入各跑一次**：

```
=== Server 没跑，输入正确 ===
请输入快递单号（输入exit退出）: 请输入手机号: 请求发生错误: Connection refused: connect

**两次一模一样。** 这一对输出同时证明了两件事：

1. `Connection refused` 就是"Server 没起"，跟输入无关（问题 14）
2. 也反过来说明：**光跑成功路径是不够的**——如果我不做这个反向实验，永远发现不了自己把"Server 没起"错怪成了"输入不对"

TCP    0.0.0.0:8000    0.0.0.0:0    LISTENING    24940

```

### 8.3 最该养成的四个习惯

这一条比上面两条都重要。

**① 拿到题目先问"数据是什么形状"，再问"用什么方法"**

这道题我卡最久的地方，是**在还不知道"JSON 长什么样"的时候，就开始想"要用什么方法"**。顺序反了。

正确的顺序是：

```
输入是什么形状？  →  中间会变成什么形状？  →  输出是什么形状？
      ↓
形状变了，才需要"工具"（fastjson / 流 / 转换）
      ↓
最后才是"哪个方法能干活"
```

**② 报错原文一个字都别改，原样贴**

我这份记录里的每一条报错，都是原样抄下来的。**改写过、概括过的报错，搜索价值基本为零**——因为你搜不到。

**③ 分清"红字"和"黄字"**

- **error**：不让你过，必须修
- **warning**：让你过，先记下来，可以晚点处理

看到控制台一片黄就慌，是很典型的浪费——**这题里那条 `URL 已过时` 从头到尾都没耽误过任何事。**

**④ 跑通 ≠ 正确**

这道题最后一次验证，我是**跑了五个分支**才敢说"通了"（成功、查不到、另一条成功、校验失败、退出）。只跑一条成功路径，等于什么都没验。

**这个习惯我是从上一题（名单排序）学来的**——那次程序和输出文件都好好的，唯一的"报警器"是我自己拿 `diff` 对了一次输入输出。

### 8.4 怎么找 API（这个要单独练）

**别背方法名，练"找方法"的能力：**

1. **看题目给的 import** —— 那就是工具箱清单（问题 11 就是从这个角度想通的）
2. **打出 `对象.` 停一下** —— IDEA 弹出所有方法
3. **`Ctrl + B`** —— 跳到类的定义，从上往下扫方法名
4. **`Ctrl + Q`** —— 看这个方法是干嘛的

### 8.5 一个具体的下一步建议

**别急着做新题。** 建议这样：

1. **把这道题关掉，从一张白纸开始重写一遍。** 不看原代码，只留题目要求。卡住了再看一眼，然后再关掉。
   
   写第二遍的速度会比第一遍快好几倍——**因为第一遍你是在"猜方向"，第二遍你知道"目标在哪"。**

2. **写完对照一下差异。** 差异的地方，就是你真正没掌握的地方。

3. **给自己加一个小需求**，比如"加一个 `/querybatch` 接口，一次查多个单号"。这一步是为了逼自己从"填空"走到"设计"。

## 九、概念小结

| 概念 | 一句话记住 |
| --- | --- |
| 抽象类不能 `new` | `HttpURLConnection` 是"交通工具"不是"自行车"。要 `url.openConnection()` 再转型 |
| `==` vs `equals` | 对象比内容只用 `equals`；`==` 比的是"是不是同一个对象"，用在 `String` 上**恒为 false** |
| 别手搓 JSON | 值要带双引号、整体要 `{}`；而且用户输入里的引号会直接拼坏它。**有工具就用工具** |
| 字段名不用你写 | **类是"键名"的来源，构造方法只管"值"**。`new Foo("pick_code:"+x)` 是把键名塞进了值里 |
| 序列化的两个方向 | **对象→纸条看 getter；纸条→对象看无参构造 + setter**。缺哪一半哪个方向就哑掉 |
| 哑失败最危险 | 编译过、跑得动、不报错，结果是错的。`==`、手拼 JSON、缺 getter 全是这一类 |
| 空 body 的后果 | `JSON.parseObject("")` **返回 null，不抛异常**；下一句就是空指针，而报错位置和出错位置隔着一条网络 |
| `sendResponseHeaders` 第二参 | 是**字节数**，不是"要不要发"。`-1` = 不带 body；中文得用 `getBytes().length` 算 |
| HTTP 顺序 | 客户端：`setXxx` 全在 `getOutputStream()` 之前。服务端：设头 → 盖章 → 写 body → `close` |
| 状态码的两种"没查到" | `400` 是"你的请求有问题"（协议层），`200 + msg` 是"请求没问题，就是没这条数据"（业务层） |
| 错误 vs 警告 | error 不让你过；warning 让你过、只是提醒。**先看开头是 `[ERROR]` 还是 `[WARNING]`** |
| import 跟类型名走 | 只在"你写出了这个类型名"时才需要；链式写法常常让模板给的 import 变成多余 |
| "……就……"是两句 | 题目里这种句式，往往是"否则……"两半。问题 10 就是只写了前半句 |
| 改数据流要顺着改 | 网络两头连着的代码，**上游先把数据发全，下游再解析**。顺序反了会撞上莫名其妙的空指针 |
| 只跑一条路径不算验证 | 成功路径跑通只说明"顺利时没事"。异常分支才是 bug 的藏身处 |
| **看堆栈，别看颜色** | 有 `at 类.方法(文件.java:行号)` 才是真报错；`WARNING:` 开头、零堆栈的直接放行 |
| **警告先看 `by` 后面是谁** | `terminally deprecated` 这类多半是**库追 JDK 慢半拍**，不是你的代码坏了 |
| **报错先问"在哪一层"** | `connect` = TCP 层，连接都没建起来；`HTTP response code` = 响应已经回来了。层次不同，方向完全不同 |
| **`Connection refused`** | **是操作系统给的**（端口上没人监听），不是服务端给的。**跟请求内容一点关系都没有** |
| **4xx 的 body 在另一条流** | 2xx 用 `getInputStream()`，**4xx/5xx 必须用 `getErrorStream()`**——否则直接抛异常 |
| **先判码，再取流** | `getResponseCode()` 是"决定走哪条路"的开关，得排在最前面。先取流、后判码，流一定取错 |
| **写在 else 里的死代码** | 不报错、不警告，编译器完全不管。**"写在那里"≠"执行过"** |
| **写 msg 要想到对面收不收** | 服务端写再多 msg，客户端不读那一条流，等于自己跟自己写信 |
| **测不到 ≠ 没写好** | 先问"**我手头这工具能不能构造出触发它的输入**"。构造不出来就换工具（curl），代码一个字别动 |
| **各握一把尺子** | 客户端验"整条链路通不通"，curl 验"服务端单方面对不对"。**只有一把尺子时，出错分不清是谁的责任** |
| **反向也要跑一次** | 正向通了，再故意造一次失败（不起 Server）。**否则你不知道"成功"是真成功，还是不管怎样都打印这个** |

### 这一轮学到的最大一件事

**问题 1～12 都是"拦路型"的**——编译不过、跑不起来、明显不对。这类问题其实好办：**红字拦着你，逼你停下来改。**

**问题 13～16 是"沉默型"的**：

| 问题 | 它的沉默方式是 |
| --- | --- |
| 13 | 程序跑得好好的，只是一直在喊我看不懂的话 |
| 14 | **我以为它在报错，其实是我在错怪它**（把"Server 没起"读成了"输入不对"） |
| 15 | 代码写在那儿、不报错、不警告，**但从来没执行过** |
| 16 | 我以为在验，其实**那个输入我的手根本构造不出来** |

**四条里没有一条会拦我。它们只会安静地让我得出错误结论。**

所以下面这句话是这轮真正的收获：

> ### **"程序没报错"和"程序是对的"，中间隔着很远。**
>
> 报错只是最低一档的信号。**比报错更危险的，是那些根本不出声、但已经错了的地方。**
