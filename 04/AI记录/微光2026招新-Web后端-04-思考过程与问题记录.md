# 微光2026招新-Web后端-04 · 思考过程与问题记录

> 记录实现「泛型仓库」这道题时，从写第一行到跑通的全过程：想过什么、错在哪、最后怎么改对的。
>
> 环境：JDK 27 / Windows 11

---

## 一、题目要求

- 创建一个**泛型接口**，它是一个仓库，要求能够储存**任何类型**的数据（使用泛型）。
- 接口内有两个方法：
  - `save()`：向仓库中添加数据
  - `getById()`：根据 id 获取数据
- 创建 `MyRepository` 类实现该接口，完成两个方法的具体实现。
  - **注意：id 是整数类型，从 0 开始自增，是数据的唯一标识。**
- 提示：可以使用 `HashMap`

---

## 二、整体思路的演变

这一步比代码本身更值得记，因为后面所有的坑都源于最初的几个模糊判断。

| 阶段 | 我当时的想法 | 后来发现的问题 |
| --- | --- | --- |
| 1 | 定义 `Repository<T>` 接口，`save` 让**外部传 id** 进来 | id「从 0 开始自增」应该是**仓库的职责**，不该甩给调用方 |
| 2 | 把发号器 `static int id` 塞进 `User` 类 | id 是"存储时的主键"，不是"Repository.User 天生自带的属性"；而且每种类型都得抄一份 |
| 3 | 想让 `User` 自己会把自己存进仓库（`User` 里 `new MyRepository<>()`） | 实体类反过来依赖容器，语义拧了；而且 `User` 里 `new User` 会无限递归爆栈 |
| 4 | 想偷偷把 `save` 改成 `private`，对外只留 `insert` | 接口是合同，实现方法的访问权限**不能收窄**，编译器直接拒绝 |
| 5 | 最终：id 由**仓库内部**发号（`nextId` 实例字段，从 0 自增）；`User` 回归纯数据类 | ✅ |

**一句话总结思路转变**：从「让数据和存储互相纠缠」→「**实体只管数据，仓库只管存储和编号**」。

## 三、逐个问题记录

### 问题 1：`implements Repository` 漏写 `<T>`，编译报三个错

**代码**

```java
package Repository;

public class MyRepository<T> implements Repository {   // ← 少写了 <T>
```

**报错**

```
Repository.MyRepository.java:3: 错误: Repository.MyRepository 不是抽象的, 并且未覆盖 Repository.Repository 中的抽象方法 save(Integer,Object)
Repository.MyRepository.java:7: 错误: 名称冲突: Repository.MyRepository 中的 save(Integer,T) 与 Repository.Repository 中的 save(Integer,Object) 具有相同名称, 但前者不覆盖后者
Repository.MyRepository.java:6: 错误: Repository.MyRepository 中的 save(Integer,T) 不会覆盖或实现超类型中的方法
```

**原因**

`implements Repository` 用的是**原始类型（raw type）**。Java 规定：继承/实现一个原始类型时，接口里的成员方法全部按**擦除后**的签名来算，于是编译器眼里接口提供的是：

```java
void save(Integer id, Object t);    // T 被擦成 Object
Object getById(Integer id);
```

而覆盖判定（JLS 8.4.2）看的是**签名是否相同或构成「子签名」**，不是看擦除后是否一样：

| 方法 | 子类签名 | 原始类型里的签名 | 结果 |
| --- | --- | --- | --- |
| `getById` | `getById(Integer)` | `getById(Integer)` | 参数完全相同 → 构成覆盖 ✅ |
| `save` | `save(Integer, T)` | `save(Integer, Object)` | 字面不同、又不是子签名 → **不构成覆盖** ❌ |

擦除之后两者都变成 `save(Integer, Object)`——**同名、同擦除参数，却不是覆盖关系**，所以编译器判定为「名称冲突」；同时接口里的抽象方法没被实现，于是又要求「类必须声明为 abstract」。

第三个错误「`@Override` 无效」是**前两条的结果**，不是独立问题。

**解决**

```java
package Repository;

public class MyRepository<T> implements Repository<T> {
```

**收获**：原始类型是泛型的"关闭开关"。只要写了 `<T>` 就一定要在 `implements` 处带上，否则泛型全部退化成 `Object`。

### 问题 2：想在 `User` 里调用 `MyRepository` 的方法，调不到

**现象**：在 `User` 的 `insert` 方法里想调用仓库的 `save`，写不出来。

**原因**（三层，逐层排查）

1. **没有接收者对象**——`save` / `getById` 都是**实例方法**（前面没有 `static`），必须有 `某个对象.save(...)`。而 `insert` 作用域里没有任何 `MyRepository` 类型的变量 → 编译器连接收者都找不到。
   - 写成 `MyRepository.save(id, user)` 也不行，`save` 不是静态方法。
2. **`hashMap` 是 private**——只有 `MyRepository` 自己的代码能访问，`User` 看不见，"绕过 save 直接操作 map"这条路也堵着。
3. **前置拦路虎**——`MyRepository` 当时还编译不过（就是问题 1）。**只要一个类编译失败，任何引用它的地方都会连带飘红。**

**解决**：把"存进仓库"这件事交给**外部调用方**（`Main`），`User` 只保留字段 + 构造器 + `toString`。

**收获**：**类可见 ≠ 对象可达。** "我在同一个 `src` 目录下定义了这个类"不代表"我能调用它的实例方法"。Java 是词法作用域 + 成员访问。

### 问题 3：把方法调用直接写在了**类体**里

**代码**

```java
public class User {
    // ...
    User user1 = new User("我", 10);   // 第 15 行
    insert(user1);                     // 第 16 行 ← 写在类体里了
    void insert(User user) { ... }
}
```

**报错**

```
Repository.User.java:16: 错误: 方法声明无效; 需要返回类型
    insert(user1);
    ^
Repository.User.java:16: 错误: 需要<标识符>
```

**原因**

类体（class body）里只能放**声明**（declaration）：字段声明、方法声明、构造器、初始化块 `{}` / `static {}`、嵌套类型。
而 `insert(user1);` 是**语句**（statement），语句只能待在方法体、构造器体或初始化块里。

编译器拿"声明"的规则去读它：`insert(user1);` 长得像 `名字(...)`，它以为在写方法声明，可方法声明得有返回类型 → 报"方法声明无效; 需要返回类型"，走到 `(` 处又报"需要<标识符>"。

**顺带一个更致命的坑**：第 15 行 `User user1 = new User("我", 10);` **能编译**（它是合法的字段声明），但它作为**实例字段**，意味着每 `new User()` 都会执行这个初始化表达式 → 又 `new User()` → 又是新的 `user1` 字段 → **无限递归，一创建 Repository.User 就 `StackOverflowError`**。

**解决**：这两行都不该出现在 `User` 里，"造一个 Repository.User 并存进仓库"是调用方的事。

**收获**

- 区分「**声明**」和「**语句**」：`类型 名字 = 初值;` 是声明，`方法名(...);` 是语句。
- **实体类里不要 `new` 自己**。类描述的是"一个 Repository.User 长什么样"，不是"顺手造个默认 Repository.User"。

### 问题 4：`main` 里"不能调用" `save`

**现象**：`main` 是静态的，`save` 是非静态的，觉得调不了。

**真相**：不是不能调，是**要用对象去调**。编译器那句"无法从静态上下文中引用非静态方法"的完整含义是：**static 方法里不能「不带接收者」地调用非静态方法**。

```java
save(0, u);             // ❌ main 里没有 this 可以借
MyRepository.save(0, u);    // ❌ 用类名也不行，save 不是静态方法
repo.save(0, u);        // ✅ 接收者明确：往 repo 这个对象里塞
```

而 `new MyRepository<>()` 在 `main` 里**完全合法**——构造器不需要"已有的对象"，它是从零造对象的，不受 static 限制。这就是为什么 `main` 里永远先 `new`、再调。

**为什么 `save` 不能改成 static？**

`MyRepository<T>` 的 `T` 是**类的类型参数**，只在实例上下文里有意义。static 方法不属于任何实例，拿不到 `T`，`HashMap<Integer, T>` 这一行就写不出来。所以 `save` / `getById` **注定是实例方法**。

**收获**：非静态方法执行时需要知道"操作的是哪个对象"（`this`）；static 方法没有 `this`，必须显式给出接收者。

### 问题 5：仓库的 `T` 要放不止 `User`

**我的想法**：一个仓库要能存多种类型。

**关键认知**：`T` 是**按「每个仓库实例」绑定**的，不是"整个 `MyRepository` 类只能服务一种类型"。

```java
import Repository.MyRepository;
import Repository.User;

MyRepository<User> userRepo = new MyRepository<>();   // 这个实例只装 Repository.User
MyRepository<Product> productRepo = new MyRepository<>();   // 这个实例只装 Product
```

两个实例、同一个类，类型各管各的——**这正是泛型存在的目的**：一套代码，服务多种类型。

**三种做法对比**

| 方案 | 写法 | 代价 |
| --- | --- | --- |
| 多实例（最常用） | `new MyRepository<User>()`、`new MyRepository<Product>()` | 无，各实例 id 独立编号互不干扰 |
| 单实例混装 | `MyRepository<Object>`，什么都能塞 | `getById` 只返回 `Object`，用具体类型**必须强转**，转错 `ClassCastException` |
| 公共父接口 | 抽 `interface Entity`，用 `MyRepository<Entity>` | 能调到公共方法，但取具体类型**仍要强转** |

**本题选择**：`MyRepository<Object>` 单实例混装——因为题目说"能够储存任何类型的数据"，且 `Main` 里确实塞进了 `User` / `String` / `Integer` 三种，运行输出正常。

**权衡说明**：混装的代价是取出来要强转；泛型的另一种典型用法（每类型一个仓库）可以做到零强转。两种都满足题目，只是取向不同。

### 问题 6：`id` 到底该放哪儿

**最初写法**

```java
public class User {
    static int id = 0;          // 它长得像"用户的 id"
    // ...
    void insert(User user) {
        myRepository.save(id, user);   // 但用起来是"下一个要发的号"
        id++;                          // 而且还在自己 +1
    }
}
```

**三个毛病**

1. **名字骗人**——它叫 `id`，干的却是"发号器"的活儿。真正的"用户的 id"根本不存在：`User` 对象自己都不知道自己是几号。
2. **`static` 意味着所有 Repository.User 共享同一个数**。`u1` 和 `u2` 看到的 `id` 永远相等；`id++` 一执行，之前所有用户的 `id` 跟着一起变。
3. **号在"插入时"才发**——同一个对象插两次就拿到两个号。号不该是插入动作的副产品。

**最终方案：发号器归仓库**

```java
package Repository;

public class MyRepository<T> implements Repository<T> {
    private final HashMap<Integer, T> hashMap = new HashMap<>();
    private int nextId = 0;          // 实例字段：每个仓库一份，天然隔离

    @Override
    public void save(T t) {
        hashMap.put(nextId, t);      // 外部完全看不到 nextId
        nextId++;                    // 自增封装在方法体里
    }

    @Override
    public T getById(Integer id) {
        return hashMap.get(id);
    }
}
```

**为什么这样最对**

- **发号器是仓库级别的**（谁存储谁编号，跟数据库自增主键一个思路）
- `nextId` 是**实例字段**，所以两个仓库各自从 0 数起，互不干扰
- id 完全不出现在方法签名里 → **调用方不需要、也无法干预发号**

**对比：为什么发号器不该放实体类**
`User` 里放一个 `static int nextId`，回头加个 `Product` 就得把发号逻辑再抄一遍——每加一种类型抄一次。而且它逼着 `User` 去关心"我怎么被存储"，把数据和存储搅在一起。

**收获**：一个变量如果同时承担两个概念（"用户的身份"和"下一个号"），迟早出事。拆成 `private final int id`（实例）+ `private static int nextId`（类）才对——不过本题里 `id` 根本不该进实体类。

### 问题 7：想把 `save` 改成 `private`、对外只留 `insert` —— 走不通

**我的想法**：`nextId++` 这种东西肯定要封装起来，不该暴露给调用方，所以把 `save` 改成 private 的内部实现，再开一个 public 的 `insert` 给外部用。

**为什么不行**

`MyRepository<T> implements Repository<T>` 是一份**合同**。接口里的方法隐式都是 `public`，一旦 `implements` 就承诺"我提供 public 的 `save(T)`"。实现时把访问权限收窄成 private，编译器直接拒绝：

- `正在尝试分配更低的访问权限；以前为 public`
- `MyRepository 不是抽象的，并且未覆盖 Repository 中的抽象方法 save(T)`

**合同条款不能降级。** 想 private 也可以，代价是删掉 `implements Repository<T>`——那就不满足题目了。

**更关键的是：封装其实早就达成了**

```java
MyRepository<Object> repo = new MyRepository<>();
repo.save(new User("我", 10));    // 调用方只知道"存进去"
```

调用方**从头到尾没见过 `nextId`**，也不知道底层是 HashMap、用的是整数序号。这就是封装 —— 封装靠的是「**private 字段 + 方法体里的实现**」，**不是**"必须再多包一层方法"。`nextId++` 已经封在 `save` 肚子里了。

**那 `insert` 还有存在的必要吗？**

如果它只写 `save(t)`，那就是**同一件事的第二个名字**，纯冗余，读代码的人会停下来想"这俩有区别吗"。

要让它有意义，就得给它**接口没有的额外能力**——把分配到的 id 返回去（`save` 因为接口签名是 `void`，做不到这件事）：

```java
@Override
public void save(T t) {
    insert(t);                   // 委托，逻辑只有一份
}

public int insert(T t) {         // 比 save 多一个返回值
    int id = nextId;
    hashMap.put(id, t);
    nextId++;                    // 全类只有这一处自增，不会漂移
    return id;
}
```

**收获**

- 「封装」≠「换个名字」。它是**让外部看不到内部细节**，而不是多套一层壳。
- **接口是承诺，不是建议**：`implements` 之后，接口方法的可见性就被钉死了。
- 两个方法做同一件事时，要么删掉一个，要么让其中一个**真的多做一件事**。

### 问题 8（附带）：`main` 少了 `public`

```java
static void main(String[] args) {   // 标准写法是 public static void main
```

在**当前环境（JDK 27）能跑**——JDK 25 起 JEP 512 放宽了入口方法的要求，不再强制 `public`。但换到 JDK 21 或更老的机器/评测机，会直接报：

```
错误: 在类 Repository.Main 中找不到主方法, 请将主方法定义为:
   public static void main(String[] args)
```

**解决**：无条件补上 `public`。这是唯一一个"在我这儿好好的、到别处就崩"的坑。

### 问题 9（附带）：`foreach` 里的 NPE 隐患

**原写法**

```java
public void foreach() {
    for (int i = 0; i < key; i++) {
        System.out.println(hashMap.get(i).toString());   // ← 取不到就是 null，直接 NPE
    }
}
```

它假设 id 一定从 0 **连续**排到 `key-1`。现在成立（只增不删），但一旦以后有删除、或者有人用别的 id 调 `save`，`get(i)` 就返回 `null`，`null.toString()` 立刻 `NullPointerException`。

**解决**：让 HashMap 自己遍历，别自己推 id。

```java
public void printAll() {
    for (T v : hashMap.values()) {
        System.out.println(v);      // println 会自动调 toString，不用手写
    }
}
```

另外 `foreach` 这个名字和 Java 的 for-each 语法容易混，叫 `printAll` 更清楚；而它**不是接口方法**，属于自己加的调试工具，超出题目要求。

## 四、最终代码

### `Repository.java`

```java
package Repository;

public interface Repository<T> {
    void save(T t);
    T getById(Integer id);
}
```

### `MyRepository.java`

```java
package Repository;

import java.util.HashMap;

public class MyRepository<T> implements Repository<T> {
    private final HashMap<Integer, T> hashMap = new HashMap<>();
    private int nextId = 0;

    // 接口要求的：只负责存
    @Override
    public void save(T t) {
        insert(t);                  // 委托，逻辑只有一份
    }

    // 自己加的：存进去，并把号码还给你
    public int insert(T t) {
        int id = nextId;
        hashMap.put(id, t);
        nextId++;
        return id;
    }

    @Override
    public T getById(Integer id) {
        return hashMap.get(id);
    }

    public void printAll() {
        for (T v : hashMap.values()) {
            System.out.println(v);
        }
    }
}
```

### `User.java`（纯数据类）

```java
package Repository;

public class User {
    private String name;
    private int age;

    public User(String name, int age) {
        this.name = name;
        this.age = age;
    }

    @Override
    public String toString() {
        return "Repository.User{name='" + name + "', age=" + age + "}";
    }
}
```

### `Main.java`

```java
package Repository;

public class Main {
    public static void main(String[] args) {
        MyRepository<Object> repo = new MyRepository<>();

        int user1Id = repo.insert(new User("name", 10));   // insert 返回分配到的 id
        int strId = repo.insert("string");
        int intId = repo.insert(1);

        System.out.println(repo.getById(user1Id));         // 用 id 取回来
        repo.printAll();
    }
}
```

**运行结果**（第一行是 `getById(user1Id)` 取回来的，后三行是 `printAll()` 遍历整个仓库）

```
Repository.User{name='name', age=10}
Repository.User{name='name', age=10}
string
1
```

## 五、概念小结

| 概念 | 一句话记住 |
| --- | --- |
| 原始类型（raw type） | 写 `implements Repository` 等于关掉泛型，所有 `T` 退化成 `Object`，还会引发「名称冲突」 |
| 覆盖判定 | 看**签名是否相同/子签名**，不是看擦除后是否一样；`getById` 能过而 `save` 不能，就差在参数里有没有 `T` |
| 声明 vs 语句 | 类体只放**声明**；方法调用是**语句**，只能待在方法体/构造器/初始化块里 |
| 实体类里不要 `new` 自己 | 作为字段会无限递归，一创建对象就 `StackOverflowError` |
| static 与实例方法 | 非静态方法需要接收者；`main` 里先 `new` 再 `对象.方法()`。用了类级类型参数 `T` 的方法**不能**是 static |
| 泛型按实例绑定 | `MyRepository<User>` 和 `MyRepository<Product>` 是两个各管各的实例，不是一个能混装 |
| 接口即契约 | `implements` 后接口方法的可见性钉死，实现时**不能收窄**权限 |
| 封装的本质 | private 字段 + 方法体里的实现，**不是**多包一层方法 |
| 发号器归属 | 谁存储谁编号 → 放仓库；实例字段保证各仓库独立编号，从 0 自增 |
