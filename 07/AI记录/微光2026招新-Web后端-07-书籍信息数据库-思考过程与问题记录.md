### 问题 1：插件界面一直转圈——根因是中文用户名

**我当时的原话**

> 我的mysql shell插件安装好了吗，这里一直在转圈一样的是什么意思

**报错原文**（VSCode 输出面板里 `MySQL Shell for VS Code` 通道）

```
Performing extension update to 2026.5.0.
Updated batch file wrappers for MySQL Shell and Router binaries in "C:\Users\星语落弦\.mysqlsh-gui".
Starting embedded MySQL Shell, using config dir 'C:\Users\星语落弦\AppData\Roaming\MySQL\mysqlsh-gui' ...
Error opening log file 'C:\Users\��������\AppData\Roaming\MySQL\mysqlsh-gui\mysqlsh.log' for writing: No such file or directory
```

（`��������` 是**花屏**，原文就是用户名 `星语落弦`——非 ASCII 的用户名在转窄字符时被搞坏了。能看清的英文部分就是 `Error opening log file ... for writing: No such file or directory`。）

**原因**

扩展启动后端时把配置目录指到了 `C:\Users\星语落弦\AppData\Roaming\MySQL\mysqlsh-gui`，路径里有中文；mysqlsh 处理不了，**找不到目录去写日志 → 进程直接退出（exit 1）**。而前端要等后端输出 `Mode: Single user` 才画界面，后端已经死了，所以永远转圈。

当时的对照实验（同一份 mysqlsh.exe，只换配置目录的取值）：

```
DIR: C:/Users/星语落弦/AppData/Roaming/MySQL/mysqlsh-gui
  err : Error opening log file 'C:/Users/��������/AppData/Roaming/MySQL/mysqlsh-gui\mysqlsh.log' for writing: No such file or directory
DIR: C:/mysqlsh-gui
  out : C:/Users/星语落弦/.vscode/extensions/oracle.mysql-shell-for-vs-code-2026.5.0-win32-x64/shell/bin/mysqlsh.exe   Ver 9.7.0 for
```

同一份 exe，纯英文目录 exit 0、中文目录 exit 1——**问题在路径，不在 MySQL**。

**解决**

第一步试的是 `setx`，**这条被否掉了**：

```
setx MYSQLSH_GUI_CUSTOM_CONFIG_DIR "C:\mysqlsh-gui"
```

`setx` 会把引号一起写进注册表，值变成 `"C:\mysqlsh-gui"`（带引号），扩展拿它当路径判断「目录不存在」，又回退到中文默认路径——**等于白设**。改用 PowerShell 直接写环境变量：

```
powershell -NoProfile -Command "[Environment]::SetEnvironmentVariable('MYSQLSH_GUI_CUSTOM_CONFIG_DIR','C:\mysqlsh-gui','User')"
```

（写这篇时我又核了一遍注册表，现在是干净值：`MYSQLSH_GUI_CUSTOM_CONFIG_DIR    REG_SZ    C:\mysqlsh-gui`。）

配套两条，缺一个都不生效：

1. **目录得先存在**——扩展是拿这个值去判断目录存不存在，不存在就回退，所以 `C:\mysqlsh-gui` 要先建出来；
2. **必须完全退出 VSCode 再重新打开**，`Reload Window` 不够——环境变量是主进程启动时读的。

还试过 8.3 短名（`dir /x` 拿 `C:\Users\STARSH~1\...`），**也否掉了**：这台机器的用户目录没有生成短名，那列是空的，用不了。

**验证**：重启之后输出里出现 `Mode: Single user`，界面正常打开；13:58 起 SQL 就能跑了。

**收获**：**「软件装了但打不开」的根因经常在它自己的日志里，而不是在你以为的那个功能上。** 我一开始怀疑的是"插件没装好"，实际是中文路径。另外，`setx` 和 PowerShell 改环境变量有个容易忽略的差别——**`setx` 会把引号写进去**。

### 问题 2：`Access denied for user 'test'@'localhost'`

**我当时的原话**（直接把报错贴上去）

```
The connection could not be opened: Access denied for user 'test'@'localhost' (using password: YES)
```

**原因**

连接模板里默认填的占位用户名 `test`，MySQL 里根本没这个账号。注意括号里那句 **`using password: YES`**——意思是"密码确实发出去了，是被服务器拒绝的"，也就是**网络是通的，只是凭据不对**（跟插件的转圈问题无关，反倒说明上一步修好了）。

**解决**

把用户名改成 `root`、密码填安装 MySQL 时设的那个，连接就通了。

**收获**：`Access denied` 和 `Connection refused / timed out` 是两类问题——**前者能连上服务器、是认证失败；后者根本没连上**。报错里的 `using password: YES/NO` 就是在告诉你密码到底发出去没有。

### 问题 3：`mysqlshell` 里「写了第一行，下面写不了了」

**我当时的原话**

> 为什么写了第一行下面写不了了

**原因**

这个扩展的 **DB Notebook 是"块（block）"模型**：一个块就是一条语句，**块下面是输出区，不是输入区**。写完第一行执行完，得按 `Ctrl+Enter`（或工具栏那个 `Execute Selection or All in Current Block and Create New Block`）才会在下面**新开一个块**，光标不会自己跑到下一行去等输入。

**解决**

1. 当场：`Ctrl+Enter` 执行 → 下面自动出现新块；
2. 长期：干脆换个编辑器——右键连接 → `Open New Connection using SQL Script`，得到的是一个普通的 `.sql` 文件，想写几行写几行，然后整段执行。

**收获**：**「写不了」有时代码没错、环境没错，是输入模型不一样。** 遇到这种"按键没反应"的界面，先搞清它接受输入的粒度（一条语句一个块 vs 一个文件），比反复按回车有用。

### 问题 5：`USE game` → `Unknown database 'game'`

**报错原文**（插件日志，2026-10-12 14:12:42）

```
mysqlsh.DBError: MySQL Error (1049): Unknown database 'game'
```

**原因**

`game` 是 04 那道题（仓库里的 `04/src/game/`）的库名，这台机器上没建过。是**手比脑子快**——切换数据库的时候顺手敲了上一个作业的库名。

**解决**

```
USE book
```

**收获**：`1049 Unknown database` 说的是「**库名**不存在」，不是表名、也不是语法。这个错和 `1146 Table doesn't exist` 要分开看：一个是库没找着，一个是库对了但表没找着。切换库的时候先 `SHOW DATABASES` 确认一下名字，比猜快。

### 问题 6：建表 1064 语法错——就多了一个逗号，改了两轮才对

**我当时的原话**（15:03:42，在排错会话里）

> 这为什么报错

（当时没把 SQL 贴过去，所以那个会话里只看到日志的调用栈，看不到我写的语句——**下面这三版的原文，是我从插件的 SQL 历史库里提出来补上的**。）

**报错原文**

```
mysqlsh.DBError: MySQL Error (1064): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near ')' at line 9
```

**第 1 版（15:02:34）——报错指向 line 9**

```sql
CREATE TABLE book(
    id INT,
    ibsn VARCHAR(50),
    title VARCHAR(100),
    author VARCHAR(100),
    publisher VARCHAR(100),
    available INT,

);
```

**第 2 版（15:02:48）——我只删了那个空行，逗号还在**

```sql
CREATE TABLE book(
    id INT,
    ibsn VARCHAR(50),
    title VARCHAR(100),
    author VARCHAR(100),
    publisher VARCHAR(100),
    available INT,
)
```

同一个错，**行号从 `line 9` 变成 `line 8`**——行号跟着空行一起动了，说明我改的位置**根本不是出错的位置**。

**第 3 版（15:04:46）——删掉 `available INT` 后面的逗号，通过**

```sql
CREATE TABLE book(
    id INT,
    ibsn VARCHAR(50),
    title VARCHAR(100),
    author VARCHAR(100),
    publisher VARCHAR(100),
    available INT
);
```

**原因**

`CREATE TABLE` 的列定义之间用逗号分隔，但**最后一个列定义后面、右括号前面不能有逗号**。报错里的 `near ')'` 就是在指："我读到这个右括号的时候，前面还留着一个多余的东西（逗号）。" MySQL 不会直接说"多了一个逗号"，只把位置指给你。

**解决经过**（时间线上挺有意思的一件事）

```
15:02:34  第 1 版，1064（line 9）
15:02:48  第 2 版，1064（line 8）      ← 只删了空行
15:03:42  在会话里问「这为什么报错」（没贴 SQL）
15:04:18  那边从错误信息推断：多半是「最后一项后面多了一个逗号」，并让我把 SQL 贴出来看是哪一行
15:04:46  第 3 版，删掉逗号 → 通过
```

从 15:02:34 到 15:04:46，前后两分十二秒——**报错其实已经把位置说得很具体了（`near ')'`），我却先去删了个空行**。

**收获**：**读报错要读"它指着一个字符"这件事。** `near ')'` 不是"括号写错了"，而是"我停在右括号这里，前后有问题"。多行 DDL 的最后一个字段后面留逗号，是最典型的写法习惯冲突（其他语言里最后一个元素带逗号往往合法，SQL 的 DDL 不行）。

### 问题 7：`UPDATE` 少了一对引号，报的却是"列不存在"

**报错原文**（插件日志，2026-10-12 15:22:20）

```
mysqlsh.DBError: MySQL Error (1054): Unknown column 'uestc' in 'field list'
```

**我当时写的**

```sql
UPDATE book
SET publisher=uestc
WHERE id=1
```

**原因**

`uestc` 是出版社名（字符串），**没有加引号**。`SET 列 = 值` 里、等号右边不带引号的裸词，MySQL 会**当成列名**去解释，于是在 `field list` 里找 `uestc` 这一列——当然没有。所以报的是 `Unknown column`，而不是语法错误。

**解决**（15:22:35，加引号，29 秒后）

```sql
UPDATE book
SET publisher='uestc'
WHERE id=1
```

**收获**：**同样的错误信息，指向的原因可以完全不同。** `Unknown column 'xxx'` 有两个常见来源：① 列名真写错了；② **字符串值忘了引号，被当成列名**。判断办法很简单——看那个名字是不是你自己写进去的一个"值"。顺带记一条：单引号是字符串的标准写法（双引号在 MySQL 里当字符串能用，但那是兼容模式，换个数据库就不认了），这次三条 INSERT 我用的双引号，后来统一用单引号。

### 问题 8（附带）：我以为"表的第一列默认就是主键"

**这条不是运行时报错**，是收尾复盘时发现的一处理解偏差——记在这里，是因为 **Task3 问的正好就是它**。

**我当时的想法**

建表时写了 `id INT` 就完事了。我以为**表的第一列会自动成为主键**（通篇教程里我没见过"要显式写主键"这一步）。

**实际上是**

主键**必须显式声明**，两种写法都可以：

```sql
-- 写在列上
id INT PRIMARY KEY

-- 或者写在最后
CREATE TABLE book(
    ...,
    PRIMARY KEY (id)
);
```

不写这两句，`id` 就只是一个普通整数列——**数据库既不保证它唯一，也不保证它不为空**，插两行 `id` 都是 1 也照样进得去。

**为什么会有这个误会**

我看的教程例子里，`students(id, name, age)` 那张表的 `id` 通常已经带了 `PRIMARY KEY AUTO_INCREMENT`，但讲的时候一笔带过，我就把"第一列"和"主键"直接划了等号。

**收获**：**约束（主键、唯一、非空、默认值）是要写进建表语句的东西，不是数据库替你猜的。** 一条 `CREATE TABLE` 里，"列有哪些"和"这些列受什么限制"是两件事，后者不写就等于没有。Task3 问我有没有选字段作唯一标识——答案就是：**选 `id`，写法 `id INT PRIMARY KEY`（再配 `AUTO_INCREMENT` 让它自己递增）**，这正是当时漏掉的那一句。

## 四、最终的表与数据

**建库**（13:59:27）

```sql
CREATE DATABASE book;
```

**建表**（15:04:46 通过的版本；后面 15:07、15:09 又补了两张表，见下）

```sql
CREATE TABLE book(
    id INT,
    ibsn VARCHAR(50),
    title VARCHAR(100),
    author VARCHAR(100),
    publisher VARCHAR(100),
    available INT
);
```

> **`ibsn` 是我敲错了**——正确拼写是 `isbn`（International Standard Book Number）。库里当时建出来的列名就是这个拼错的版本，上面照抄的是原文，没改。

字段与类型的取舍：

| 字段 | 类型 | 为什么这么选 |
| --- | --- | --- |
| `id` | `INT` | 用一个整数编号标识图书记录（我按约定拿它当唯一标识，**但这句建表里没有显式声明主键**，见下） |
| `ibsn` | `VARCHAR(50)` | 图书编号 ISBN（**这里我拼错了列名，正确是 `isbn`**）。它**可能有前导 0 和连字符**，用整型会把 `0` 吃掉，所以用字符串 |
| `title` | `VARCHAR(100)` | 书名是变长文本，给 100 足够 |
| `author` | `VARCHAR(100)` | 同上 |
| `publisher` | `VARCHAR(100)` | 出版社名，变长文本（很可能为空，所以没设 `NOT NULL`） |
| `available` | `INT` | 可借数量，整数 |

**三条数据**（15:12:07 / 15:12:44 / 15:13:34）

```sql
INSERT INTO book(id,title,author) VALUES(1,"微积分","lbs");
INSERT INTO book(id,title,author) VALUES(2,"线性代数","wyz");
INSERT INTO book(id,title,author) VALUES(3,"程算","zy");
```

三条只给 `id`、`title`、`author`，没有给的字段（`ibsn`、`publisher`、`available`）就是 `NULL`。

**这张表没有主键（收尾复盘时确认的）**：建表语句里 `id INT` 只是**普通列**，既没有 `PRIMARY KEY`，也没有 `AUTO_INCREMENT`。原因是我当时以为"**表的第一列默认就是主键**"——教程里没提过要显式声明，我就没写。这是个误解：**主键必须自己写出来**，不写的话数据库层面既不管 `id` 唯不唯一、也不管它空不空。这一点在答卷 Task3 里如实交代。

## 六、概念小结

| 概念 | 一句话记住 |
| --- | --- |
| 报错里的 `near 'X'` | 不是"X 写错了"，而是"**我读到 X 这里停住了，它前面有问题**"。`near ')'` = 右括号前面多了东西（DDL 里最常见的就是最后一个字段后面的逗号） |
| `1049 / 1064 / 1054` | 1049 = **库**名不存在；1064 = **语法**错（位置靠 `near`）；1054 = **列**名不认识（也可能是字符串忘了引号） |
| 字符串要引号 | `SET publisher=uestc` 里的裸词会被当成**列名**；字符串用**单引号** |
| `VARCHAR` vs `INT` | 有前导零、带符号的编号（ISBN、学号、电话）一律用字符串——用整型会把开头的 `0` 吃掉 |
| 没给值的列 | 就是 `NULL`（"没有值"），跟 `0`、空字符串不是一回事 |
| 主键与唯一标识 | 唯一标识是**选出来、并且显式声明**的：`id INT PRIMARY KEY`。**同名书靠的从来不是书名**——两本《微积分》各占一行，靠 `id` 区分。我这张表当初只写了 `id INT`、没声明主键，"第一列默认就是主键"是错的 |
| 约束是写出来的 | `PRIMARY KEY` / `AUTO_INCREMENT` / `NOT NULL` / `UNIQUE` / `DEFAULT` 都属于"对列的约束"，**不写就等于没有** |
| DB Notebook 的"块" | 一个块一条语句，执行后按 `Ctrl+Enter` 才会新开一块；想随便写多行就用 SQL Script 编辑器 |
| 中文用户名 | `C:\Users\<中文名>` 这类路径会让一批命令行工具（含 mysqlsh）在写日志/临时文件时失败，症状往往是"启动不了、一直转圈"。对策：把配置目录指到纯英文路径 |
| `setx` 的坑 | 它会把引号一起写进注册表（`"C:\mysqlsh-gui"`），程序读到的值和你想的不一样；要精确控制就用 PowerShell 的 `SetEnvironmentVariable` |
| 环境变量什么时候生效 | 进程启动时读，所以**要完全退出程序再开**，`Reload Window` 之类不够 |
| 图形化 vs 命令行 | `mysql.exe`（经典客户端，只有 SQL）、`mysqlsh.exe`（MySQL Shell，SQL + JS/Python + `util.*`）、各种图形界面都是这三个外面的壳；对数据库本身没有任何区别，差别只在连接管理、编辑体验 |
| 装了语言包找不到菜单 | 用 `Ctrl+Shift+A` 按**动作名**搜（中文界面搜中文名），别背英文菜单路径 |
